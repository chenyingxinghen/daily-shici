# 04 · 客户端设计

> 技术栈：**Kotlin 2.0.21 + Jetpack Compose**，已有单模块 `:app` 脚手架（AGP 8.11.2 / minSdk 24 / compileSdk 36）。
> 本文只设计**客户端**。接口契约见 `02`，服务端见 `03`，数据包格式见 `01 §6`。
> 客户端的形态是**本地优先**：已下载的内容全部离线可用，网络只是补足与更新。

---

## 1. 模块分层

### 1.1 保持单模块

现有工程是单模块 `:app`。**不建议拆多模块**：

| 拆多模块的理由 | 本项目是否成立 |
|---|---|
| 加速增量编译 | ❌ 85 万首数据在服务端，客户端代码量不大 |
| 强制分层边界 | ⚠️ 单模块内用**包结构 + 依赖规则**即可，靠自律 |
| 多团队并行 | ❌ 个人项目 |
| 动态交付（Dynamic Feature） | ❌ 数据包走网络下载，不用 App Bundle 的动态模块（那有 4 GB 限制且需走 Play） |

拆模块会引入 `build.gradle.kts` 维护、`api`/`implementation` 依赖传递、编译配置重复等成本，收益在单人项目里接近零。**先单模块，等 `:app` 编译超过 30 秒再谈拆分。**

### 1.2 包结构

```
com.example.daily_shici/
  data/
    local/          # Room：Entity / Dao / Database / Migration
    remote/         # Retrofit：ApiService / DTO / 拦截器
    pack/           # 数据包：下载、校验、解压、批量入库
    repository/     # ★ 唯一对外数据出口，决定走本地还是网络
  domain/
    model/          # 领域模型（与 DTO / Entity 分离）
    search/         # LIKE 搜索、高亮区间计算
    daily/          # 每日一诗缓存与兜底选诗
  ui/
    daily/          # 每日一诗
    browse/         # 浏览（筛选）
    search/         # 搜索
    detail/         # 详情
    library/        # 收藏与历史
    packs/          # 数据包管理
    theme/          # ★ 已存在
  work/             # WorkManager：包下载、每日预取、通知
  di/               # Hilt Module
```

**依赖方向单向**：`ui → domain → data`。`data` 不反向依赖 `ui`/`domain`。这条规则靠 code review 保证，是单模块方案唯一的约束成本。

### 1.3 依赖

在 `gradle/libs.versions.toml` 追加：

| 用途 | 库 |
|---|---|
| 本地数据库 | Room 2.6.x（含 KSP 编译器） |
| 网络 | Retrofit 2.11 + OkHttp 4.12 + kotlinx-serialization |
| DI | Hilt 2.51（含 `hilt-navigation-compose`） |
| 异步 | kotlinx-coroutines（Compose 已带） |
| 后台任务 | WorkManager 2.9 |
| 键值存储 | DataStore Preferences（存设置、catalog_version） |
| 分页 | **Paging 3**（`/poems` 列表与本地列表统一用 `PagingSource`） |
| 图片 | 无（v1 不展示图片） |

**不引入**：Hilt 之外的 DI 框架、Moshi（用 kotlinx-serialization 避免反射）、任何中文分词库（见 §6）。

## 2. Room Schema

### 2.1 设计原则

客户端 schema **不是**服务端 schema 的镜像。三处刻意的差异：

1. **服务端的 `author` / `dynasty` 维表在客户端退化为文本列。** 包里写的就是作者名与朝代名（`01 §6.2` 的反范式化决策），客户端没必要还原成维表再做 JOIN —— 85 万行 JOIN 是纯浪费。
2. **`author_id` 不出现在客户端主键里。** 它是服务端分配的，离线包里没有（`02 §3.8`）。**本地作者导航键是归一化后的作者名。**
3. **客户端有本地表**（收藏、历史、包状态、每日缓存），服务端完全没有（`02 §6.2`）。

### 2.2 表定义

索引**必须与查询模式逐一对应**（对应 `03 §2.2`）。`poem` 实体的完整声明：

```kotlin
@Entity(
  tableName = "poem",
  indices = [
    Index(value = ["weight", "poemId"]),                  // 默认列表排序
    Index(value = ["dynasty", "weight", "poemId"]),
    Index(value = ["period", "weight", "poemId"]),        // 顶部 Tab
    Index(value = ["genre", "weight", "poemId"]),
    Index(value = ["cipai", "weight", "poemId"]),
    Index(value = ["author", "weight", "poemId"]),        // ★ 作者名，非 author_id
    Index(value = ["packId"]),                            // 卸载包时批量删
  ]
)
data class PoemEntity(
    @PrimaryKey val poemId: Long,
    val title: String,
    val content: String,          // \n 分行
    val excerpt: String,          // 首行，列表用
    val author: String,           // ★ 归一化作者名，本地导航键
    val dynasty: String,
    val period: String,
    val genre: String,
    val form: String?,
    val cipai: String?,
    val lineCount: Int,
    val charCount: Int,
    val isPublicDomain: Boolean,
    val weight: Int,
    val packId: String,           // 来源包，卸载时按此删除
)
```

> ⚠️ **Room 的 `Index` 不支持列级排序方向。** 服务端索引是 `(weight DESC, poem_id ASC)`（`03 §2.2`），而 Room 建的索引一律升序。**这不影响正确性** —— SQLite 可反向扫描索引满足 `ORDER BY weight DESC`，但反向扫描时 `poemId` 也一并变 `DESC`，与契约要求的 `poemId ASC` 相反。
>
> **因此客户端必须显式写 `ORDER BY weight DESC, poemId ASC`，接受 SQLite 无法完全用索引满足排序**。实测验证：2 万行规模下这个排序的代价可忽略（毫秒级）。**这是客户端与服务端索引的一处已知差异**，不影响 `02 §5.1` 的粗排序承诺。

### 2.3 不建的表

| 不建 | 原因 |
|---|---|
| `author` / `dynasty` 维表 | 退化为 `poem` 的文本列（§2.1） |
| FTS 表 | v1 搜索用 `LIKE`（§6） |
| `user` / `token` | 无账号（`02 §6.1`） |

### 2.4 迁移策略

**v1 不写任何 `Migration`。** 理由是数据全部可重新下载：一旦 schema 变更，`fallbackToDestructiveMigration()` 清库，然后重新导入 `seed` 包（内置，秒级）+ 用户已装的包需重下。

这对用户是可接受的（数据包下载有进度与断点续传），对我们则省掉全部迁移代码。

**何时必须改为真迁移**：当用户数据不可重建时 —— 即收藏与历史。**v1 起就应把 `favorite` / `reading_history` 放进独立的 Room Database（另一个 `.db` 文件）**，使其不受诗词库 schema 变更影响：

```
shici_poems.db     # poem / collection / installed_pack / daily_cache —— 可破坏性重建
shici_user.db      # favorite / reading_history —— 永不清空，需真迁移
```

**这是本设计里唯一一处"为未来付费"的结构决策**，成本是两个 `RoomDatabase` 类，收益是用户收藏永远不会因为诗词库升级而丢失。

## 3. 数据包下载与入库

### 3.1 流程

```
获取清单(/packs) → 用户选择 → 下载(.jsonl.gz) → 校验 sha256
    → 流式解压逐行解析 → 批量 insert → 记录 installed_pack → 通知 UI
```

### 3.2 断点续传

包是不可变的（`02 §3.9`），故可用 HTTP `Range` 续传：

- 下载到 `cacheDir/packs/<pack_id>.part`，记录已下载字节数到 DataStore。
- 中断后重新入队，带 `Range: bytes=<已下载>-`。
- 服务端返回 `206` 则续传；返回 `200`（不支持 Range）则**从头重下**并清除偏移记录。
- **不存 ETag 做条件请求** —— 包不可变，`sha256` 已是更强的校验（`01 §6.3`）。

下载用 WorkManager 的 `ForegroundInfo`（`02` 未涉及，但 29 MB 的包必须给用户可见进度）。

### 3.3 流式入库

`d2-ming` 包 gzip 后 28.7 MB，解压后约 82 MB —— **不可整个读进内存**。

```kotlin
GZIPInputStream(FileInputStream(partFile)).bufferedReader().useLines { lines ->
    val batch = ArrayList<PoemEntity>(2000)
    for (line in lines) {
        batch += json.decodeFromString<PackPoemDto>(line)
        if (batch.size >= 2000) { dao.insertAll(batch); batch.clear() }
    }
    if (batch.isNotEmpty()) dao.insertAll(batch)
}
```

要点：

- **批大小 2000。** Room 的 `insertAll` 在单事务内执行；2000 条约 700 KB，是内存与事务开销的平衡点。
- **整个入库包在一个事务里会耗尽 WAL。** 分事务提交，代价是中断时留下部分数据 —— 用 `installed_pack` 记录**只在全部成功后才写入**，UI 据此判断包是否可用；部分数据的 `poem` 行带 `packId`，失败重试前先按 `packId` 删除（`DELETE FROM poem WHERE packId = ?`），保证幂等。
- **`content` 的 `\n` 是真实换行**（`02 §1.1`）。包内是 `\\n` 转义（`01 §6.2`），JSON 解析后自然还原为 `\n`，**不需要额外处理**。
- **进度 = 已解析行数 / manifest.poemCount**，比按字节算更准（gzip 解压速率不均）。

### 3.4 并发与取消

- 同时只跑一个下载/入库任务。WorkManager 用 `ExistingWorkPolicy.KEEP` 按 `pack_id` 唯一命名。
- **用户取消时**：停止任务 → 按 `packId` 删除已入库行 → 删除 `.part` 文件。三者顺序不可颠倒（先删数据再删文件，否则文件没了数据还在）。
- **入库期间不阻塞 UI**：`poem` 表在入库过程中逐步可查，用户能立刻看到已导入的部分。

### 3.5 卸载包

```sql
DELETE FROM poem WHERE packId = ?;      -- 索引 idx_packId 支持
DELETE FROM collection_member WHERE poemId NOT IN (SELECT poemId FROM poem);
DELETE FROM installed_pack WHERE packId = ?;
```

**收藏与历史不动。** 用户卸载了某个包，其收藏的诗会变成"未下载"状态（§5），重新下载后自动恢复 —— 这是 `favorite` 表与 `poem` 表分离的直接好处。

`seed` 内置包**不可卸载**（`builtin = true`）。

## 4. 仓库层：本地优先

### 4.1 决策规则

所有读取走同一个模式：**先本地，缺了再网络，网络结果写回本地。**

```kotlin
suspend fun getPoem(id: Long): PoemDetail? =
    localDao.findById(id) ?: api.getPoem(id)?.also { cacheToLocal(it) }
```

但**不是所有端点都这样**，需分类：

| 数据 | 策略 |
|---|---|
| 诗词正文 | **本地优先，绝不因网络结果覆盖本地**。本地是权威（来自校验过的包） |
| 筛选器 `/facets` | 本地缓存优先；无缓存才请求，成功后写 `facets_cache` |
| 每日一诗 | 缓存优先（`daily_cache`）；当日有网则刷新 |
| 包清单 `/packs` | **必须网络**。失败则用 `installed_pack` 渲染"已装"状态 |
| 搜索 | **有网走服务端 `/search`；无网回退本地 `LIKE`**（§6.3） |

### 4.2 在线与离线结果的差异处理

`02 §5.2` 要求"未下载"是显式 UI 状态。落地为一个密封类型，**禁止返回空列表蒙混**：

```kotlin
sealed interface ListResult {
    data class Ok(val items: List<PoemSummary>) : ListResult
    data class NotDownloaded(val packIds: List<String>) : ListResult   // 提示下载
    data class Empty(val filters: AppliedFilters) : ListResult         // 真的没有
}
```

判定"该内容未下载"的方法：查询命中 0 条时，**不直接返回 Empty，而是查 `facets_cache` 里该筛选条件下的应有条数**（来自服务端 `/facets`）。应有条数 > 0 而本地为 0 → `NotDownloaded`。

这条逻辑值得单独实现并测试 —— 它是"用户以为 App 坏了"与"用户知道该下载什么"的分界线。

## 5. 每日一诗

### 5.1 预取

```kotlin
// 每日一次（WorkManager PeriodicWork，约束：联网）
suspend fun prefetchDaily() {
    val last = dataStore.dailyCacheMaxDate()
    val from = maxOf(today(), last?.plusDays(1) ?: today())
    val days = min(30, ChronoUnit.DAYS.between(from, today().plusDays(30)).toInt())
    if (days <= 0) return
    api.getDailyBatch(from, days).items.forEach { dao.upsert(it.toEntity()) }
}
```

- **只补缺口**：从 `daily_cache` 的最大日期 +1 开始请求，避免重复拉 30 天。
- 缓存上限保留 **365 天**（超过则删最旧），防止无限增长。
- **失败不重试到死**：WorkManager 默认的 `BackoffPolicy.EXPONENTIAL` 即可，网络恢复后系统会重跑。

### 5.2 三级读取（对应 `02 §5.3`）

```
1. 有网 且 今天未请求过      → GET /daily → 写缓存 → 展示
2. 无网 或 请求失败          → 读 daily_cache[today] → 展示（与在线体验一致）
3. 缓存未命中（断网超 30 天） → 本地兜底选诗 → 展示并标注"离线精选"
```

第 3 级的池子 = **本地已下载的全部 `poem` 行**（`02 §4.3`）：

```kotlin
// 确定性挑选：同一天多次打开必须得到同一首，否则用户体验是"这 App 在乱跳"
val count = dao.countAll()
val seed  = date.toEpochDay() * 2654435761L      // Knuth 乘数，日期 → 伪随机种子
val offset = ((seed % count) + count) % count     // 保证非负
dao.pickAtOffset(offset)
```

```sql
-- pickAtOffset：只取一行，故允许 OFFSET（与 03 §3.4 的随机漫游同一理由）
SELECT * FROM poem ORDER BY poemId LIMIT 1 OFFSET :offset
```

> ⚠️ **不要用 `ORDER BY (poemId * A + :daySeed) LIMIT 1`。** 该表达式是 `poemId` 的**单调递增函数**（`A > 0`），`ORDER BY` 的结果与 `ORDER BY poemId` 完全等价，日期种子不产生任何影响 —— 每天都会返回同一个最小 `poemId`。这是个看起来很像随机、实际毫无随机性的写法。**必须用取模打散**（上面的 `offset` 方案）或保证非单调的哈希。

### 5.3 通知

WorkManager `PeriodicWork`，每日固定时刻（默认 08:00，可在设置调整）：

- **触发前检查**：今天是否已读过？（`reading_history` 有今日记录则不发）
- 点击通知 → `PendingIntent` 打开详情页，`poemId` 从 `daily_cache` 取。
- **Android 13+ 需 `POST_NOTIFICATIONS` 运行时权限**，被拒后不再询问（改用设置页入口）。
- **不做精确闹钟**（`AlarmManager.setExact`）—— WorkManager 的 ±15 分钟偏差对"每日一诗"完全可接受，而精确闹钟在 Android 12+ 需 `SCHEDULE_EXACT_ALARM` 特殊权限，不值当。

## 6. 搜索（本地 `LIKE`）

### 6.1 实现

```sql
-- 三段式实现"标题 > 作者 > 正文"的粗排序（02 §5.1）
SELECT poemId, MIN(tier) AS tier, weight FROM (
  SELECT poemId, 0 AS tier, weight FROM poem WHERE title   LIKE '%'||:q||'%' ESCAPE '\'
  UNION ALL
  SELECT poemId, 1 AS tier, weight FROM poem WHERE author  LIKE '%'||:q||'%' ESCAPE '\'
  UNION ALL
  SELECT poemId, 2 AS tier, weight FROM poem WHERE content LIKE '%'||:q||'%' ESCAPE '\'
)
GROUP BY poemId
ORDER BY tier ASC, weight DESC, poemId ASC
LIMIT :limit OFFSET :offset
```

要点：

- **必须写 `MIN(tier)`，不能只写裸列 `tier`。** SQLite 允许 `GROUP BY` 时选裸列，但取的是**任意一行**的值而非最小值 —— 一首诗标题和正文都含"月"时，若不取 `MIN`，它可能被归入 `tier=2`（正文档），"标题优先"就失效了。这是本查询唯一的易错点，需单测覆盖"标题与正文同时命中"的用例。
- `weight` 用裸列是安全的：它**函数依赖于 `poemId`**（同一首诗只有一个权重），故取任意行都得同一个值。
- **`ORDER BY tier ASC, weight DESC, poemId ASC`** 完全对应 `02 §5.1` 的粗排序承诺。
- **`LIKE` 的通配符需转义**：用户输入的 `%` `_` `\` 必须转义，否则 `%` 会匹配一切。三处 `LIKE` 都要带 `ESCAPE '\'`（上面已加），转义本身在 Kotlin 侧做。
- **不用 Paging 3 的 `RemoteMediator`** —— 本地搜索是单次查询，`PagingSource` 直接返回即可。

### 6.2 性能

| 已装内容 | 正文规模 | `LIKE` 全扫耗时（估） |
|---|---|---|
| `seed`（1.2 千首） | 0.4 MB | < 5 ms |
| 1–2 个包（约 2 万首） | 2–7 MB | 10–50 ms |
| 全量（85 万首） | 283 MB | 数百 ms |

**结论：离线路径用 `LIKE` 是安全的。** 用户极少下满全量（283 MB），而常见规模下 `LIKE` 比 FTS 更快（省了索引维护）。上表的"数百 ms"只在下满全量且断网时才会遇到，可接受。

若未来实测全量搜索超 500 ms，再引入 FTS —— 届时须同时决定分词方案（见 `02 §8` 决策记录）。但注意：**这只影响离线路径**，在线搜索本就由服务端的 FTS5 承担（§6.3）。

### 6.3 有网走服务端，无网才用本地

| 状态 | 数据源 | 覆盖范围 |
|---|---|---|
| **有网** | 服务端 `/search`（`02 §3.6`） | **全量 859,591 首** |
| **无网** | 本地 `LIKE`（§6.1） | 已下载内容 |

**有网时必须搜服务端。** 服务端是全量的严格超集，本地只是子集 —— 所以在线时**用服务端结果直接替换本地结果即可，无需合并**（合并两套不同打分体系的排名只会引入复杂度而无收益）。

> ⚠️ **这里曾有一个错误决策**，记录于此以免重犯：早期设计写的是"`/search` 客户端不调用，在线也搜本地"，理由是"调服务端会搜到未下载的诗，点进去没正文"。**该推理方向是反的** —— 正确做法是**返回这些结果并标注"未下载"**，而不是不返回它们。
>
> 后果原本会很严重：新装用户只有 `seed` 的 1,192 首，搜"李白"几乎搜不到东西。**搜索是发现功能，完整性就是它的全部意义** —— 这正是最不该做本地限制的地方。
>
> 教训：识别出失败模式后，要分清修法是「**避免该情形**」还是「**处理该情形**」。此处标注优于隐藏：用户搜到了才知道有这东西可下载；隐藏则他永远不知道它存在。

**未下载结果的标注**（与 §4.2 同一原则）：服务端返回的 `poem_id` 若不在本地 `poem` 表，显式标记"未下载"，点击后：

- 有网 → 直接 `GET /poems/{id}` 拉详情展示（可读，只是没离线副本）
- 同时提供"下载所属包"入口

**边打边搜**：为兼顾即时性与完整性，采用两级：

1. **本地 `LIKE` 立即出结果**（10–50 ms，§6.2），用户键入即有反馈
2. **防抖 300 ms 后请求服务端**，用完整结果替换

这样每个按键都不会打一次网络，同时最终结果覆盖全量。

**离线时** UI 必须明示"仅在已下载内容中搜索"（`02 §5.2`）—— 离线搜不到是**真实的能力边界**，不是 bug，要如实告知。

> **一处已知不对称**（极端情况，v1 不处理）：若服务端开了 `INCLUDE_COPYRIGHTED=false`（`02 §6.4`），而用户在开关生效前已下载了 `d2-modern` 包，则本地能搜到服务端不再返回的诗。此时在线搜索反而比离线少 —— 属合规开关的预期副作用。

### 6.4 高亮区间（`02 §2.3` / `03 §4.5`）

契约规定 `highlights` 的索引按 **Unicode 码点**计，而 Kotlin `String` 是 UTF-16：

```kotlin
// 契约索引（码点）→ Kotlin String 索引（UTF-16 code unit）
fun codePointToCharIndex(s: String, cpIndex: Int): Int =
    s.offsetByCodePoints(0, cpIndex)

// 本地搜索时反向：Kotlin 索引 → 码点索引
fun charIndexToCodePoint(s: String, charIndex: Int): Int =
    s.codePointCount(0, charIndex)
```

**必须两端各写单测**，用含生僻字的样本（如 `01 §3.4` 提到保留繁体的那批）验证。少写这一步的后果是：平时全部正常，只有生僻字的高亮位置偏移 —— 这种 bug 极难在测试外被发现。

**来源不同，处理不同**（§6.3）：

| 路径 | `highlights` 来源 |
|---|---|
| 在线 | 服务端 `/search` 响应直接给出（`02 §2.3`），客户端只做码点换算 |
| 离线 | 本地 `LIKE` 自行计算命中位置，再转成码点索引后交给同一个渲染组件 |

两条路径产出的是**同一个数据结构**，故 UI 层无感知 —— 这是把 `SearchHit` 定义成纯数据（而非标记串）的额外收益。

## 8. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 模块划分 | **保持单模块 `:app`**，包结构分层 | 单人项目拆模块收益接近零，成本是构建配置维护 |
| 客户端 schema | **不用维表**，作者/朝代退化为 `poem` 的文本列 | 包里本就是反范式化的名字（`01 §6.2`），还原维表再做 JOIN 是纯浪费 |
| 作者本地导航键 | **归一化作者名，非 `author_id`** | `author_id` 是服务端分配的，离线包里没有（`02 §3.8`） |
| Room 数据库拆分 | **诗词库与用户库分两个 `.db`** | 诗词库可破坏性重建（省全部迁移代码），用户收藏必须保住 |
| 搜索 | **本地 `LIKE`，不建 FTS** | 离线路径的常见规模（≤2 万首）下比 FTS 更快且无分词依赖（§6.2）。在线路径走服务端 FTS5 |
| 搜索的数据源 | **有网走服务端，无网用本地 `LIKE`** | 服务端是全量超集，在线时替换而非合并；未下载结果**标注**而非过滤（§6.3） |
| 每日兜底选诗 | **按日期确定性打散，非随机** | 同一天多次打开应是同一首，否则像"App 在乱跳" |
| 通知 | **WorkManager Periodic，不做精确闹钟** | ±15 分钟偏差对该功能无损；精确闹钟需特殊权限 |
| 迁移 | **v1 用 `fallbackToDestructiveMigration`**（诗词库） | 数据可重新下载；用户库单独隔离不受影响 |
| 包下载校验 | **只校验 sha256，不用 ETag** | 包不可变，sha256 是更强的保证 |

## 9. 遗留问题

1. **Room 索引无法指定 `DESC`，与服务端 `03 §2.2` 的索引定义有差异**（§2.2）—— 需实测全量数据下 `ORDER BY weight DESC, poemId ASC` 的排序代价。2 万行规模预计无感。
2. **入库 28.7 MB 包（`d2-ming`）的耗时未实测** —— `01 §6.2` 预估 30–60 秒，须真机验证；若超 90 秒需重估包格式（`01 §6.2` 已留 SQLite 分片预案）。
3. **同时下载多个包的排队策略未定** —— §3.4 定为"只跑一个"，但用户可能一次性勾选 5 个包。需要队列（`WorkManager` 的 `beginUniqueWork` 链式）还是逐个确认？
4. **`facets_cache` 与已下载包的差异**（§4.2）—— "应有条数"来自服务端全量统计，而本地可能只装了一部分。"未下载"判定需按**包粒度**而非全局计数，实现时需细化。
5. ~~**深色模式下的正文排版未设计**~~ —— 已定论：设计稿只提供「素纸朱栏」一套浅色方案，
   深色模式**未设计**，因此客户端不提供主题切换，只在「主题与排版」页如实展示当前令牌。
   详见 §10.5。
6. ~~**`compileSdk 36` / `minSdk 24` 下的 Compose BOM 版本偏低**~~ —— 已定论，方向与本文原判断**相反**：
   应把 androidx 整组**收敛到 compileSdk 36 时代**，而不是上调 Compose BOM。详见 §10.1。

## 10. 实现记录（客户端已按设计稿落地）

> 本节记录**实现时的事实**，与前面的**设计意图**区分开。凡与前面冲突之处，以本节为准。

### 10.1 依赖与工具链（硬约束，勿随意升级）

| 组件 | 版本 | 约束来源 |
|---|---|---|
| Gradle | 8.13 | AGP 8.13 要求 Gradle ≥ 8.13 |
| AGP | 8.13.2 | 8.x 线最后一档；AGP 9 有 breaking change，未采纳 |
| Kotlin / KSP | 2.2.20 / 2.2.20-2.0.4 | 与 AGP 8.13 匹配 |
| compileSdk / minSdk | 36 / 24 | 本机 SDK 仅到 android-36 |
| Hilt | **2.57.2** | **2.60+ 的 Hilt Gradle 插件硬性要求 AGP ≥ 9.0.0**，会直接 `Failed to apply plugin` |
| Compose BOM | 2025.06.01 | 对应 compose 1.8.3 |
| Room / WorkManager / Paging | 2.7.2 / 2.10.1 / 3.3.6 | 均须与 compileSdk 36 对齐 |
| androidx core-ktx / activity / lifecycle | 1.16.0 / 1.10.1 / 2.9.1 | 同上 |

**关键结论：androidx 依赖的上界由 `compileSdk` 决定，不是「越新越好」。**
脚手架最初声明的 core-ktx 1.19 / activity 1.13 / lifecycle 2.11 / compose BOM 2026.09
要求 **AGP ≥ 9.1 且 compileSdk ≥ 37**，而本机 SDK 只装到 android-36，
平台包 37 的下载源（dl.google.com）在当前网络下不可达 ——
因此整组依赖必须收敛到 compileSdk 36 时代，**这与 §9.6 原先「建议上调 Compose BOM」的建议相反**。

另：`minSdk 24` 下 `java.time` 不可用，客户端大量使用 `LocalDate`，
故开启 `isCoreLibraryDesugaringEnabled` 而不是抬高 minSdk（`app/build.gradle.kts`）。

### 10.2 内置 seed 包

`assets/seed_pack.jsonl`（70 首）由 `tools/build_seed.py` 从 `tools/seed_source.txt` 编译而来。

- 源数据用 `|` 分隔的纯文本，**不手写 JSON** —— 包格式是 JSONL，`content` 里的换行必须是
  转义的 `\n`，手写极易出错且错了不报错、只是正文少一行。
- seed 与网络下载包**共用同一条入库代码路径**（`PackInstaller.importLines`），
  因此 seed 成了下载链路的日常验证载体，而不是只跑一次的旁路。
- seed 包 `builtin = true`，**不可卸载**。

### 10.3 「未下载」三态的落地

`ListResult`（§4.2）落在 `PoemRepository.describeEmpty(filters)`：
本地命中 0 条时，取 `facets_cache` 中该条件下的**应有条数**，
`expected > localTotal` 即判为 `NotDownloaded`，否则 `Empty`。

候选包用**粗粒度推断**（列出所有未安装包），不做更细的猜测 ——
「猜错这个包有你要的诗」比「让你自己看清单」更糟。

### 10.4 视觉实现要点（对齐设计稿）

- **图标全部手绘**（`ui/components/ShiciIcons.kt`，Canvas + Path，20 单位坐标系）。
  Material Icons 是实心风格，与稿子的 1.25 / 1.333 细线描边不符。
- **「浏览」底栏图标**：画布文件里节点 4:248 与 4:254 是**同一个放大镜**（几何逐值一致），
  但本项目此前已决议把「浏览」改为司南罗盘（见 `.workbuddy/memory/2026-09-22.md`）。
  当前文件应是在重建时丢失了该修正，实现按**既定决议**走罗盘。
- **每日一诗与详情页整体垂直居中**（立轴式排版，内容块几何中心落在内容区中点）。
  用 `CenteredScrollColumn` 实现「内容短则居中、长则可滚动」——
  直接给带 `verticalScroll` 的 Column 加 `Arrangement.Center` 是**无效**的，
  滚动容器内容高度等于子项高度，没有可分配的多余空间。
- **每日一诗日期行**「乙巳年 九月廿二 · 星期二」用系统 `android.icu.util.ChineseCalendar`
  换算，不塞农历查表（表要覆盖 1900–2100 约 200 个整数，抄错一位就是一整年错位）。
  注意它依赖 android.icu，**只能跑仪器测试**，JVM 单测拿不到该类。
- **高亮索引必须做码点换算**（§6.4）：契约是 Unicode 码点，Compose `AnnotatedString` 是
  UTF-16 char。少这一步平时全对，只有生僻字位置偏移 —— 已由
  `SearchTextTest` 用代理对样本（U+2000B）锁住。
- **浏览页两级筛选**：第一行选维度，第二行选取值。设计稿把「全部」和「唐」**同时**画成选中态，
  那是两张状态叠在一起的产物；实际交互只能有一个当前取值，故按「维度 → 取值」实现，
  且切维度会清空取值（否则会出现「停在体裁页签却带着朝代=唐」的鬼状态）。

### 10.5 主题与排版页

设计稿只给了一套浅色方案。客户端**不提供**深色模式切换，而是在「主题与排版」页
如实列出当前色板与字体族 —— 编造一套未设计过的深色配色，代价比承认「还没设计」大得多。

### 10.6 尚未验证的部分

- **服务端不存在**，`/packs`、`/poems`、`/search`、`/daily`、`/facets` 全部无法联调。
  因此所有网络路径都以「失败则退回本地/离线提示」实现，但**真实契约的字段名与形状未经实测**。
- **数据包下载链路（Range 续传 / sha256 校验 / 流式 gunzip 入库）无真包可验**，
  代码按 §3 的设计写完，但只在 seed 导入路径上跑通过同一条入库逻辑。
- 未在真机/模拟器上做视觉走查，仅完成编译与单元测试。

### 10.7 状态栏：删掉自绘，并强制深色图标（2026-09-23）

**问题**：真机上「系统状态栏与 App 背景文字对比度极低」。

**根因**：`enableEdgeToEdge()` 默认用 `SystemBarStyle.auto`，它**跟随系统深色模式**决定
图标明暗。用户开深色模式时系统给浅色（白）图标，而本 App 恒为浅色纸底 `#FAF5EB`
（§10.5：只有一套浅色方案）→ 白字压浅底，几乎不可见。
这是「App 只有一套浅色方案」与「系统栏跟随系统主题」之间的必然冲突。

**修法**（两处共同兜住）：

| 位置 | 做法 |
|---|---|
| `MainActivity` | 显式传 `SystemBarStyle.light(TRANSPARENT, TRANSPARENT)`，两个系统栏恒为深色图标 |
| `values/themes.xml` | `windowLightStatusBar = true`；statusBar / navigationBar 透明 |
| `values-v27/themes.xml` | 追加 `windowLightNavigationBar = true`（该属性 API 27+，故单独放） |

**同时移除自绘状态栏**：原先画死 `9:41` 与假信号/电池图标，真机上等于状态栏显示两遍。

- `ScreenStatusBar` → `SystemStatusBarInset`：只让出 `WindowInsets.statusBars` 的高度，
  **不再写死 62dp**（刘海屏、无刘海屏、平板各不相同）。
- 底栏加 `windowInsetsPadding(WindowInsets.navigationBars)`，否则标签会被手势条压住点不到。
- 连带删除死代码：`StatusBarIcons`（自绘矢量）、`ShiciText.StatusTime`、
  `StatusBarPadding/Top/Height` 三个尺寸令牌、`colors.xml` 里模板遗留的 `purple_*` / `teal_*`。

### 10.8 App 图标：朱红印章（2026-09-23）

图标复用设计稿唯一的视觉锚点 —— 印章：**朱红 `#C53A2A` 底 + 纸色 `#FAF5EB`「詩」**。

**用确定性栅格化，不用 AI 生图。** 理由是印章的核心就是那个「詩」字，
而图像模型渲染汉字极易走形（多笔、少笔、变成花纹）。本机装有
`C:\Windows\Fonts\NotoSerifSC-VF.ttf` —— **正是设计稿指定的字体** ——
用它精确取字形，既准确又可复现。

`frontend/tools/make_app_icon.py` 产出：

| 产物 | 用途 |
|---|---|
| `drawable-*/ic_launcher_foreground.png` | 自适应图标前景（纸色「詩」+ 透明底） |
| `mipmap-*/ic_launcher.png` / `ic_launcher_round.png` | 传统图标（圆角方印 / 圆印），API < 26 用 |
| `drawable-*/ic_notification_poem.png` | 通知栏小图标（**纯白**「詩」，系统会着色，必须单色） |
| `tools/icon_preview.png` | 512px 预览，供人眼确认 |
| `drawable/ic_launcher_background.xml` | 朱红实底（108×108） |

自适应图标的字形占 108dp 画布的 **52%**，即安全区（66dp）的约 85% —— 再大就会被
圆形/方形遮罩切到笔画。`monochrome` 层复用前景，供 Android 13+ 主题图标着色。

模板遗留的 `ic_launcher_foreground.xml`、`ic_notification_poem.xml`
与 10 个 `.webp` 已删除（同名资源不能以不同格式共存于同一目录）。

### 10.9 内置数据包：唐诗三百首 + 宋词三百首（2026-09-23）

内置内容从原先 70 首手写占位，改为**上游真实数据**：`tang-300`（366 首）+
`song-300`（280 首）= 646 首，id 区间 1..646。

产出链路（ETL 的首个切片）：

```
CanvaChen/llm-dataset-chinese-poetry  (Apache-2.0)
  data/全唐诗/唐诗三百首.json  366 首
  data/宋词/宋词三百首.json    280 首
        ↓  backend/etl/build_builtin_packs.py
        │   lib/text.py  归一 + 派生（去重键、char_count、form、cipai）
        │   lib/ids.py   IdAllocator：poem_id 一经分配永不改变
        │   mappings/builtin_sets.json  内置包定义（weight=100 即 W3 选本层）
        ↓
  backend/packs/{tang-300,song-300}.jsonl + .manifest.json
        ↓  自动复制
  app/src/main/assets/{tang-300,song-300}.jsonl + builtin_packs.json
```

**客户端不硬编码包列表**：`PackInstaller.importBuiltins()` 遍历
`assets/builtin_packs.json` 导入。新增内置包只需重跑 ETL，Kotlin 侧零改动。

两处实现要点：

- **边解析边算 sha256**（`DigestInputStream`）——既校验包体完整性，又不必把整个包读进内存。
  校验失败或条数与 manifest 不符时**回滚该包**（`deleteByPack`）：
  否则用户看到的是「少了几首」而不是报错，这类静默缺失极难排查。
- 导入时顺带登记 `collection` / `collection_member`，详情页因此能显示「收录于《唐诗三百首》」。
- `uninstall` 改为**按内置索引**判定不可卸载（原先硬编码 `"seed"`）。

### 10.10 ⚠️ 待修：客户端 DTO 与 `02` 契约不一致（2026-09-23 发现）

写后端前通读 `docs/02-API契约.md`，发现 §10 之前写的客户端 DTO 是**按猜测建的、与契约不符**。
由于 `Json { ignoreUnknownKeys = true }` 且各字段都有默认值，**解码不会报错，只会静默取默认值** ——
属于最危险的一类不一致（编译通过、单测通过、真机上一片空白）。

必须逐项对齐（**服务端实现以 `02` 为准，客户端改**）：

| 位置 | 现状 | 契约（`02`） |
|---|---|---|
| 全部 DTO 字段名 | camelCase（`poemId`） | **snake_case**（`poem_id`），须逐字段加 `@SerialName` |
| `PoemDetail.author` | `String` | **对象** `{author_id, name, dynasty}` |
| `PoemDetail.collections` | `List<String>` | **对象数组** `[{slug, name}]` |
| `SearchHit` | `{poem, highlights:[{field,ranges}]}` | 扁平 `{poem_id,title,author,dynasty,hit,snippet,highlights:[[start,end]]}` |
| `/poems` 响应 | `{items,total,notDownloadedPackIds}` | `{items,next_cursor,total,applied_filters}` |
| `/packs` 响应 | 缺 `tier`/`min_poem_id`/`max_poem_id`/`download_url` | 全部要有 |
| `/facets` 响应 | `period/dynasty/genre/theme` + `value` | `periods/dynasties/genres/cipais/collections` + `key`/`name`/`count` |
| 查询参数取值 | 传中文（`dynasty=唐`） | 传 key（`dynasty=tang`） |

最后一条要特别处理：**在线用 key、离线用 name**。`02 §3.8` 已定「本地导航键是作者名，
`author_id` 仅用于在线」，朝代同理 —— 故 `FacetOption` 必须**同时带 key 与 name**，
而不是二选一。
