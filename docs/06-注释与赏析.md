# 06 · 注释、译文与赏析

> `02-API契约.md §6.3` 从 v1 起就预留了 `annotation` / `translation` / `appreciation`
> 三个字段并恒返 `null`，说明「二期用 LLM 生成后回填」。本文是那个二期的落地记录 ——
> 但**做法与最初的设想不同**，方向由用户在两轮讨论中厘清，见 §1。

本文回答五件事：**两条路各解决什么、内容从哪来、怎么保证不出错、放在哪、怎么跑起来。**
全部结论都有实测数据支撑，测量环境见 §6.1。

---

## 1. 两条路，不是一个方案

用户明确划出了两条互不替代的路径：

| | 方式一 | 方式二 |
|---|---|---|
| 形态 | **用户就具体词句提问 → AI 按需检索 → 流式作答** | **预制注疏（从网络找现成数据）** |
| 内容 | 模型现场组织 | **真人编辑成果** |
| 覆盖 | **任意一首** | 7,388 首（占全量 0.88%） |
| 延迟 | 首字 1–3 s，随后逐字 | 零（纯查表） |
| 落库 | **不落库** | 落 `annotations.db` |
| 解决什么 | 冷门诗、具体疑问、千奇百怪的问题 | 经典篇目读得**深**、有据可查 |

### 1.1 为什么不能用「让 LLM 批量生成注释 JSON」代替这两条

这是本项目走过的一段弯路，记录下来避免重蹈：

1. **不可靠。** 古典诗词注释是**考据**，不是创作。「白日」是太阳还是白昼、
   「鹳雀楼」在今山西何处 —— 这些答案在模型权重里是模糊的。
   实测中模型会把《登幽州台歌》里「怆然」的读音写成 `chuáng rán`，
   而同一段回答的前半句又写着 `chuàng` —— **自相矛盾且用户无从分辨**。
2. **无法流式输出。** 生成是「凑齐一整份 JSON 才算成功」的任务，不产出增量，
   用户只能盯着空白等。
3. **等待极其漫长。** 本地模型单首 30–60 s（§6.3）。全量 83.4 万首不做考虑，
   即便是精选的两千首也要 30 小时以上。

而方式二用**已有的真人注疏**替掉了这部分生成需求（更可靠、零等待），
方式一用**问答**替掉了「覆盖冷门诗」的需求（按需、流式、不落库）。

> 一句话总结这个分工：**注疏解决「读得深」，问答解决「问得到」。**

## 2. 方式二：数据从哪来

### 2.1 结论先行：公开数据里**不存在「全量注释」**

注疏是**编辑劳动**，不是可供抓取的既有事实。全量 83.4 万首诗词中，
能拿到真人注疏的数量级是**万级**，不是十万级。任何「覆盖全量」的方案
最终都只能靠生成 —— 而那正是 §1.1 否决掉的路。

所以方式二的目标不是全量，而是**把有真人注疏的那部分尽量收全**，
剩下的交给方式一。

### 2.2 选定主数据源

**`Papersnake/gushiwen`（HuggingFace，古诗文网镜像，`license: cc0-1.0`）**

| 项 | 实测值 |
|---|---|
| 文件 | 单个 `gushiwen.jsonl`，**745,360,892 B**（0.75 GB） |
| 行数 | 433,841 |
| 许可 | **CC0-1.0**（可商用，无署名义务） |
| 最后更新 | 2024-10-16 |
| 下载 | 11.6 MB/s，约 64 s（HF 直链） |

备选与排除：
- `tang10086/gushiwen` —— 同内容的新副本（行数、字节完全一致），**无额外覆盖**，不必下第二份。
- `ABear/Poetry_CN`（OpenDataLab，7.1 GB，聚合国学迷/读古诗词/古诗句/古诗文网四站）
  —— 覆盖面可能更大，但许可是 **MBODL-BY-NC-SA（非商用）**，且下载多需登录。列为后续评估项。
- 出门问问「序列猴子古诗今译」—— **68 万首**译文，覆盖率最高，但只有译文、
  且是翻译模型的训练集（质量存疑），无法满足注释/赏析需求。
- `open-chinese/poetry-collection`（37 万首）—— **主数据模型里没有注疏**；
  它的 `appreciation/` 是 **AI 生成**的鉴赏，与 §1.1 的方案同类，不予采用。

### 2.3 ⚠️ 上游行的结构与两个字段陷阱

```json
{"tb_gushiwen": {"nameStr": "静夜思", "author": "李白", "chaodai": "唐代",
                 "cont": "<p>床前明月光…</p>", "yizhu": "9933003333ff", …},
 "tb_fanyis":   {"fanyis":   [{"nameStr": "译文及注释",
                               "cont": "<p><strong>译文<br/></strong>…</p><p><strong>注释</strong><br/>…</p>"}]},
 "tb_shangxis": {"shangxis": [{"nameStr": "创作背景", "cont": "…", "cankao": "…"},
                              {"nameStr": "赏析",     "cont": "…", "cankao": ""}]},
 "tb_author":   {…}}
```

**陷阱一：`tb_gushiwen.yizhu` 不是注释正文。** 它是形如 `'9933003333ff'` 的
**校验位掩码**。真正的译文与注释都在 `tb_fanyis.fanyis[*].cont` 里，
而且**译文和注释同处一个 HTML 块**，靠内层 `<strong>译文</strong>` /
`<strong>注释</strong>` 两个标题分段。按 `yizhu` 取正文会得到一串十六进制垃圾。

**陷阱二：`cankao` 可能是 `'0'`。** 那是上游的「无出处」占位符，
不过滤客户端就会显示「参考资料：0」。

**另：上游没有可回溯的页面 URL。** `shiID` / `shiIDnew` 实测恒为 0，也没有 slug。
故 `source_url` 用**站内检索链接**替代：
`https://so.gushiwen.cn/search.aspx?value=<标题>`
（⚠️ 必须用 `so.` 子域；`www.gushiwen.cn/search.aspx` 会 302 到登录页）。

## 3. 方式二：匹配

上游与我方的**题名习惯不同**，精确题名只能命中一半：

| 情形 | 上游 | 我方 |
|---|---|---|
| 组诗合并 | `关山月` | `关山月二首 其一` / `其二` |
| 词牌·首句 | `夜行船·忆昔西都欢纵` | `夜行船` |
| 带宫调 | `双调·寿阳曲·江天暮雪` | `双调·寿阳曲` |

所以匹配分两级，**每一级都用正文相似度把关**：

1. **精确题名** —— `(归一化作者, 归一化标题)` 直接命中；
2. **题名主干** —— 剥宫调 → 取 `·` 之前 → 反复剥组诗序数，同作者下取候选里正文最像的一首。

### 3.1 为什么用相似度而不是子串包含

两边的正文存在**版本异文**：

| 上游 | 我方 | 相同字数 |
|---|---|---|
| 一**迳**入云斜 | 一**径**入云斜 | 39/40 |
| 陶渊明之卧舆遇酒**便于于道上** | 陶渊明之卧舆遇酒**便留于道士** | 148/152 |

用「一段是否包含另一段」判定，会把**这些正确的匹配全部误杀**
（实测精确同名也只通过 46%）。改用**字符二元组 Dice 系数**后，
上述两例分别得到 0.95 与 0.97。

### 3.2 阈值是怎么定的（实测）

取我方 83.4 万首中 **4,000 对随机不同诗**做基线：

```
随机配对相似度： p50 = 0.00   p95 = 0.00   p99 = 0.02   max = 0.04
```

即**两首不同的诗，相似度几乎必然 ≤ 0.04**。取阈值 `MATCH_THRESHOLD = 0.6`，
是噪声上限的 **15 倍**：

| 阈值 | 接受首数 |
|---|---|
| 0.0（只按题名） | 8,140 |
| **0.6（采用）** | **7,463 候选 → 7,388 入库** |
| 0.7 | 7,301 |
| 0.9 | 6,411 |

阈值筛掉的 677 首（8,140 → 7,463）都是**版本异文过多导致正文对不齐**的真匹配 ——
这是有意的保守：**宁可少收，也不把注疏挂到错的那一首上。**

### 3.3 主干匹配为什么必须带正文消歧

同作者同词牌往往有好几首（辛弃疾光是《好事近》就多首）。
只按主干取「第一个」会把注疏挂到**错的那一首**上 —— 用户读到的是别人的考据，
**比没有注疏更坏**。正文相似度是唯一能区分它们的信息。

### 3.4 匹配结果可审计

入库时记录 `match_kind`（`exact` / `stem`）与 `match_score`：

```
exact 4,909 首 / stem 2,479 首
```

**这不是装饰。** 将来若发现某条挂错了，能按 `kind`/`score` 批量筛出来复核，
不必重跑整个导入。实测最低分的 8 条主干匹配（0.60–0.61）逐条人工看过，
**全部正确**，且成因一致：上游把组诗合成一条、我方拆成其一/其二，
Dice 恰落在 0.60–0.61 —— 这正说明阈值选得准。

## 4. 方式二：存储

注疏存在 `backend/server/data/annotations.db`，**与 `poems.db` 分开**。

`etl/lib/pipeline.py:329` 的 `stage_load` 第一件事就是 `DB_PATH.unlink()` ——
**每次重跑 ETL 都会把 `poems.db` 整个删掉重建**。注疏虽可从源数据重导，
但两个库的生命周期本来就不同：

| | `poems.db` | `annotations.db` |
|---|---|---|
| 来源 | ETL 全量重建 | 外部数据导入 |
| 可变性 | 构建产物，**只读** | 增量 |
| 谁写 | `backend/etl/` | `scripts/import_gushiwen.py` |

分开还让注疏可以单独备份与迁移。代价是没有外键 —— 有意的取舍。

### 4.1 表结构

```sql
CREATE TABLE poem_annotation (
  poem_id        INTEGER PRIMARY KEY,
  translation    TEXT,             -- 译文
  annotation     TEXT,             -- 注释
  appreciation   TEXT,             -- 赏析（含鉴赏/简析/评析等，多条已合并）
  background     TEXT,             -- 创作背景
  citation       TEXT,             -- 文献出处，多条以「；」分隔
  source         TEXT NOT NULL,    -- 数据源标识，如 'gushiwen'
  source_url     TEXT,             -- 可达的原站入口
  license        TEXT NOT NULL,    -- 许可标识，如 'CC0-1.0'
  upstream_title  TEXT,            -- 上游原始标题（回溯用，非冗余）
  upstream_author TEXT,
  match_kind     TEXT,             -- 'exact' | 'stem'
  match_score    REAL,             -- 正文 Dice 相似度
  imported_at    TEXT NOT NULL
);
```

**每个字段都带来源与许可不是装饰**：这张库装的是**别人的编辑成果**，
`source` / `source_url` / `license` 回答「这条内容从哪来、能不能商用」，
是将来合规审查时的唯一凭据。**新增数据源时必须填。**

> 与旧版（LLM 生成）的差别：旧 schema 有 `status`/`origin`/`provider`/`model`/
> `prompt_ver`/`attempts`/`last_error` 与一张 `annotation_queue`，
> 那套是为「按需生成 + 入队」设计的。需求纠正后方式二不再生成
> （方式一是问答，也不落这张库），故全部移除：
> **这张表现在只有「有」与「没有」两种状态**（有行 = 有注疏）。

### 4.2 客户端缓存

Room 里有一张 `poem_annotation`（`ShiciPoemsDatabase` v3）。
为什么值得缓存：注疏是真人编辑成果，服务端只有 0.88% 的诗有，
而用户离线时它得还在 —— 否则「本地优先」这个定位就漏了一块。
写库策略是**只写不删**：服务端返回空时不动缓存，避免把用户已能看到的注疏弄没。

> **Room 迁移的坑（已踩）**：v2 → v3 时我最初只写了 `ALTER TABLE ADD COLUMN`，
> 但 v3 去掉了 v2 的 `model` / `generatedAt` 两列 ——
> Room 迁移后会把实际表结构与预期 schema **严格比对，多一列少一列都会崩在首次打开**，
> 且报错信息很含糊。SQLite 又没有 `DROP COLUMN`（3.35 之前），
> 所以必须走「建新表 → 拷数据 → 删旧表 → 改名」。
> 改完用 Python 的 sqlite3 建 v2 表、跑迁移、与 `3.json` 比对结构，**逐字一致**后才收工。

## 5. 方式二：接口

### 5.1 `GET /poems/{id}`（有改动）

`PoemDetail` 的三个字段**不再恒 `null`**：已收录返回内容，未收录仍返回 `null`。
另新增三个可选字段（`02 §7`：向后兼容的加法不需要升版本）：

- `annotation_background` —— 创作背景
- `annotation_citation` —— 文献出处
- `annotation_sources` —— `[{title, url}]`，指向古诗文网站内检索页

`annotation` 是**扁平字符串**，逐条注释按「词：义」一行一条（上游本身就是这个形态）：

```
幽州：古十二州之一，现今北京市。
幽州台：即黄金台，又称蓟北楼，故址在今北京市大兴，是燕昭王为招纳天下贤士而建。
前：过去。
古人：古代那些能够礼贤下士的圣君。
```

### 5.2 `GET /poems/{id}/annotation`（新增）

只读。**只有 `ready` / `missing` 两种状态**：

```json
{
  "poem_id": 2, "status": "ready",
  "annotation": "…", "translation": "…", "appreciation": "…",
  "background": "…", "citation": "王运熙 等．唐诗鉴赏辞典．上海：上海辞书出版社，1983：46-47",
  "sources": [{"title": "古诗文网（CC0-1.0）", "url": "https://so.gushiwen.cn/search.aspx?value=…"}],
  "source": "gushiwen", "license": "CC0-1.0"
}
```

未知 `status` 一律按 `missing` 处理 —— 服务端将来加状态时，
老客户端的表现是「显示提问入口」，这是所有降级方式里最不坏的一种。

### 5.3 已移除的端点

`POST /poems/{id}/annotation`（请求生成）**已删除**。把它留着会让客户端以为
「还能按需生成」，而实际已经没人消费那个队列了。测试里有一条用例专门断言它返 405。

## 6. 方式一：流式问答

### 6.1 测量环境

| 项 | 值 |
|---|---|
| GPU | RTX 4050 Laptop，**6 GB 显存** |
| 模型 | `qwen3.5:9b`（Ollama，Q4） |
| 权重与显存 | 模型 **8.67 GB**，其中只有 **4.43 GB** 进显存，其余溢出到 CPU |
| 实测吞吐 | 恒定约 **8 tok/s**（受限于显存溢出，不是 GPU 算力） |

### 6.2 ⚠️ 必须关掉思考链（性能命门）

同一任务，只差一个 `think` 参数：

| | `completion_tokens` | 耗时 | 正文长度 |
|---|---|---|---|
| 开启思考 | **3365** | **445 s** | 357 字 |
| 关闭思考 | **221** | **28 s** | 427 字 |

**约 15 倍，输出质量无可见下降。** 问答是交互场景，这个差距直接决定能不能用。

> ⚠️ **Ollama 的 OpenAI 兼容层不认 `think` 字段。**
> 因此 `ollama` provider 走**原生 `/api/chat`**，这是唯一能关掉它的路径。
> 另外：把 `/no_think` 写进 system prompt **没有效果**（实测仍出 3365 tokens）。

### 6.3 实测延迟

| 场景 | 首字 | 整段 |
|---|---|---|
| 「怆然」怎么读（短答，57 段） | ~2 s | **13.5 s** |
| 「古人」指谁（长答） | ~2 s | **32.6 s** |

8 tok/s ≈ 2–3 汉字/秒。**流式让等待变得可接受，但没有让它变快** ——
这是这个硬件下的上限。想更快只有换显卡、换小模型或走云端 API（§8.3）。

### 6.4 为什么是 SSE

需求是**单向**的（客户端发一个问题，服务端逐字推回答）。WebSocket 的双向通道、
心跳、自定义帧全用不上，却要承担握手、保活、代理兼容性成本。
SSE 是普通 HTTP，穿透任何反代与移动网络。

用 POST 而不是 `EventSource`（只支持 GET）是因为**客户端是 Android**（OkHttp 直接读流），
不受该限制；而问题文本放 query string 里要编码、长度受限、还会进访问日志。

**事件协议**（`text/event-stream`）：

```
event: sources   data: {"items":[{"title","url"}],"searched":true}
event: delta     data: {"text":"幽"}
event: done      data: {"ok":true}
event: error     data: {"message":"…"}
```

两个实现细节：
- 响应头必须带 `X-Accel-Buffering: no` —— 否则 nginx 会把流缓冲到结束再一次性吐出，
  流式白做。
- **异常一律变成 `error` 事件而不是 HTTP 500**：流已经开始（状态码早已发出 200），
  此时只能靠事件通道上报。

### 6.5 检索策略：只用摘要，不抽整页

生成式任务可以慢慢抽两页正文（每页约 6 s），因为它不在乎延迟。
**问答不能**：用户盯着屏幕等首字。

实测检索返回的 `snippet` 本身已经是注释开头（该服务直接返回页面正文节选），
所以方式一**只用 snippet**，把首字延迟压在 2 s 内；`extract()` 仍保留给离线/批处理用。

**检索失败不阻断作答**：退化为只用原文作答，并切换到一套**更保守的系统提示**
（明确禁止考据类内容、读音没把握就说「以辞书为准」）。理由是
用户问「这首诗的作者是谁」本来就不需要检索，为检索失败拒答是舍本逐末。

### 6.6 检索由谁决定：模型自主 + 考据类强制兜底

#### 6.6.1 为什么让模型自己组词（命中率实测）

早期版本是「服务端按固定模板检索 → 把资料塞给模型」。实测这种模板**命中率很差**：

| 检索词 | 命中 |
|---|---|
| 唐 王昌龄 《横吹曲辞 出塞 一》 这首诗里的生僻字词是什么意思？ | **0 条** |
| 王昌龄《横吹曲辞 出塞 一》 秦时明月汉时关，万里长征人未还。 | **6 条** |

**自然语言问句对搜索引擎是纯噪声，正文首句才是对这首诗最强的锚点。**
改版后把 `search` 工具暴露给模型（`qwen3.5:9b` 的 capabilities 含 `tools`，已验证可用），
由它决定要不要搜、搜什么 —— 实测它能组出 `怆然的拼音及读音` 这种精准的检索词。

#### 6.6.2 但不能全交给模型：考据类问题强制先检索

实测发现：把「要不要检索」完全交给 9B 模型**不稳定**（3 次里跑了 2 次）。
其中一次它没调工具、凭记忆答出：

> 「将」读音为 **jiàng**… 在《将进酒》这首诗中，「将」字读音为 **jiāng**

**自相矛盾，且两个都错**（正确是 **qiāng**）。

所以按问题类型分流（`ask.needs_evidence`）：

| 问题类型 | 路径 |
|---|---|
| **考据类**（读音/典故/背景/地名/异文/作者/释义） | 服务端**先检索**再作答，模型仍可自己再搜一次补充 |
| 其它（字面理解、修辞、整体感受） | **模型自主**决定是否调 `search` |

考据类走预检索还有个**意外的好处：更快** —— 让模型先决定要不要搜要多花一轮
（10–30 s），而预检索只要 3 s，跳过的这一轮正好抵掉检索开销。
所以「强制检索」在这个硬件上**既不慢也不劣**，只是去掉了模型犯错的机会。

#### 6.6.3 提示词里必须强调「倾向于多查一次」

⚠️ 这一条是实测调出来的。系统提示里若写「不要为了调用而调用 —— 每多一次调用用户就多等」，
**9B 模型会真的不调用**（三个用例全部 `searched=false`，改为凭记忆作答）。
改成把代价讲反过来的表述后才正常触发：

> ⚠️ 拿不准就调用。检索只要 2 秒，而答错会直接让用户读错一首诗 ——
> 这个代价完全不对称，**倾向于多查一次**。

### 6.7 ⚠️ 已知弱项：读音会被编（两处提示词都拦不住）

考据类已强制检索，但**读音仍是硬伤** —— 各诗词站点的 snippet 通常**不标注拼音**，
于是模型在没有依据时仍会编。实测同一首诗、三种防护下的结果：

| 防护 | 结果 |
|---|---|
| 无守卫 | 「读音是 jiāng（一声）」，并加一句「并非读作 qiāng」——主动错误 |
| 守卫放**用户消息末尾** | 完全无视守卫，继续给音 |
| 守卫放**系统提示** | 仍给了 **jiāng**，但至少补了「资料中未标注读音，请以辞书为准」 |

结论：**这是本地 9B 模型的能力上限，不是提示词写法问题。** 现行实现保留了
`pronunciation_guard`（资料里检测不到注音时明令禁止给音）作为减伤措施，
它能让答案带上免责说明，但**无法保证不出错音**。

真正的解法只有两条：
1. **换更强的模型**（云端 API，见 §8.3）—— 最直接有效；
2. **给语料补拼音** —— 我们导入的真人注疏里本来就含 `怆（chuàng）然`、`殢（tì）`
   这类标注（判据：汉字后紧跟拉丁串）。可以把它们抽成结构化读音表，
   读音类问题**直接查表回答**，完全绕开模型。这属于后续可选项（§10）。

> 判据细节也踩过坑：`Bring in the Wine, by Li Bai` 这类英文页面标题
> 会被「任意拉丁串」误判成拼音，必须要求**汉字后紧跟**拼音或括号。

### 6.8 ⚠️ 必须把已有注疏喂给模型（实测发现的缺陷）

最初实现里，问答只给了诗的正文 + 检索资料。实测问「『怆然』怎么读」时模型答：

> 「怆」（chuàng），「怆然」读音为 chuáng rán

**前后自相矛盾** —— 而我们的注疏里明明写着「怆（chuàng）然」。

修法是把本诗已有注疏拼进提示词，**且排在检索资料之前**，并声明「可靠，优先采信」：

```
【诗】…
【本诗已有的注疏】（真人编辑内容，可靠，优先采信）
注释：… 怆（chuàng）然：悲伤凄恻的样子。 …
【参考资料】…
【用户的问题】…
```

修后同一问题的回答：

> 「怆」字读音为 chuàng，「怆然」（chuàng rán）意为悲伤凄恻的样子。**根据本诗注疏**…

**手里有权威内容却不给模型，等于让它凭印象猜。** 系统提示里也加了一条
「注音必须逐字核对，注疏里标了音的一律以注疏为准」。

### 8.3 想更快怎么办

方式一的瓶颈是硬件，不是代码。三条路，都不需要改架构：
1. **走云端 API** —— `SHICI_LLM_PROVIDER=openai` + `SHICI_LLM_BASE_URL` 指向
   DeepSeek / 硅基流动 / 自建 vLLM，延迟通常降到 1–3 s、首字亚秒。
2. **换更小的模型** —— 8.67 GB 权重塞不进 6 GB 显存是根本原因；
   一个能全量进显存的 4B 级模型会把吞吐翻几倍（质量需实测）。
3. **换显卡**。加线程无用：显存溢出时并发只会让两边都更慢。

## 9. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 注疏内容来源 | **从网络导入真人注疏**，不用 LLM 生成 | 生成不可靠（实测注音自相矛盾）、无法流式、单首 30–60 s |
| 冷门诗怎么办 | **流式问答**（方式一），不生成注疏 | 问答按需、流式、覆盖任意一首；生成则要预跑几十小时 |
| 问答是否落库 | **否** | 一次问答针对某个具体问题，不是对整首诗的系统注疏；落库会让「有没有注疏」含义模糊 |
| 主数据源 | `Papersnake/gushiwen`（CC0-1.0） | 许可最干净、可直连下载、字段含译文+注释+赏析+出处 |
| 匹配方式 | 题名主干 + **正文 Dice 相似度**双层 | 上游题名习惯不同（组诗合并/词牌·首句/宫调）；子串判定会误杀版本异文 |
| 匹配阈值 | `0.6` | 实测随机配对 max 0.04，是噪声上限的 15 倍 |
| 多候选消歧 | **按正文相似度选**，不取第一个 | 同作者同词牌有多首，取第一个会挂错诗 —— 比没有注疏更坏 |
| 匹配证据 | **入库 `match_kind` / `match_score`** | 挂错时能批量筛出来复核，不必重跑导入 |
| 存储位置 | **独立 `annotations.db`** | ETL 会 `unlink` 重建 `poems.db` |
| 客户端缓存 | Room v3（写真实迁移，整表重建） | 离线要能读；虽然源可重导，但离线时拿不到 |
| 检索由谁决定 | **模型自主调 `search` 工具**，但**考据类问题强制先检索** | 模型能组出更准的检索词（命中率 0→6）；但实测把选择权全给它时 3 次跑 2 次，考据类答错代价太高 |
| 检索词构造 | **正文首句做锚点**，绝不拼用户问句 | 自然语言问句对搜索引擎是噪声：实测同一首诗 0 条 vs 6 条 |
| 提示词中的检索倾向 | 明写「**倾向于多查一次**」 | 写「不要为了调用而调用」时 9B 模型真的不调用（三个用例全 `searched=false`） |
| 工具轮次 | **1 轮** | 多轮命中率更高，但每轮多约 20 s 才出字 |
| 工具结果回填 | 必须先补一条含 `tool_calls` 的 assistant 消息 | Ollama/OpenAI 都要求 assistant 先出现，缺了直接报错 |
| 模型直接作答 | **尊重它**，并如实告知客户端「未检索」 | 强行检索是浪费；但用户有权知道这条答案查没查证 |
| 读音无注音时 | 明令禁止给音（守卫放**系统提示**） | 减少编造；但仍拦不住 9B 模型，见 §6.7 |
| 已有注疏 | **必须进问答提示词且排在检索资料之前** | 实测少了它模型会把「怆然」答成 chuáng rán |
| 传输协议 | **SSE（POST）** | 单向推送；WebSocket 的双向与保活全用不上 |
| 流中途出错 | 已吐字则**只记日志**，不算失败 | 用户看到了半句回答，此时弹「出错了」只会困惑 |
| 空区块 | **连标题一起不渲染** | `02 §6.3` 硬要求 |
| 「没有注疏」的文案 | **不写「加载失败」**，并给出路到问答 | 0.88% 覆盖率下「没有」是常态，说成失败会让用户以为 App 坏了 |

## 10. 遗留问题

1. **覆盖率天花板是数据问题，不是技术问题。** 公开数据里只有约 1.1 万首有真人注疏，
   我们能匹配到 7,388 首。想更高只能另找数据源（`ABear/Poetry_CN`，
   非商用许可，见 §2.2）或者对少数据定向检索后回填。
2. **诗经 0 覆盖**（0/305）。上游数据集不含诗经注疏，需要单独解决。
3. **`weight` 分层在 ETL 里没有生效**（库内全为 1）。这不影响本质疏功能
   （它按合集白名单与匹配算法选目标），但同时意味着 `02 §4.1` 的加权随机、
   `/poems` 的默认排序都退化成了均匀/无区分 —— **这是独立缺陷，需单独修**。
4. **匹配仍有约 3,900 首配不上**，抽查显示多为「我方没有这首诗」
   （如《东城高且长》《庄辛说楚襄王》）以及少量题名差异极大的情形。
   可考虑引入按首句匹配作为第三条路径。
5. **问答体验受限于 8 tok/s**。流式缓解了感知，但没有解决速度（§8.3）。
6. **⚠️ 读音会被编，这是本地 9B 的能力上限**（§6.7）。两处提示词位置都拦不住。
   减伤措施已上（`pronunciation_guard`），但真要可靠只能换模型或给语料补拼音。
   后者可行：我们导入的真人注疏里本就含 `怆（chuàng）然` 这类标注，
   可抽成读音表直答，绕开模型。
7. **问答不保留历史**。用户问过什么、答过什么，关掉页面就没了。
   若要做「问答历史」，需要新的存储与 UI，属独立需求。
7. **`source_url` 是站内检索链接而不是原页 URL** —— 上游没给原页地址。
   用户在古诗文网站内还需要再点一次。可用 AnySearch 逐首反查原页 URL 后回填
   （约 7,400 次检索，按 2 s 计约 4 小时），属可选优化。
8. **未做问答内容的合规复核**。方式一的回答由模型生成并直接展示，
   没有留存与审计。当前是自用项目，可接受；公开发布前需要补。
