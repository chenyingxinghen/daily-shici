| 覆盖 | 先秦 → 当代 |

### 1.2 记录格式

全库统一为**扁平 JSON 数组**，每条 4 个字段：

```json
{
  "id": "caocao#1",
  "title": "度关山",
  "author": "曹操",
  "content": "天地间，人为贵。\n立君牧民，为之轨则。\n…"
}
```

- `content` 以 `\n` 分行，**换行是唯一的结构信息**，必须原样保留（诗体推断、排版渲染都依赖它）。
- 上游已完成两项归一：**繁体转简体**（少数生僻字保留繁体以确保 Android/Linux 正常显示）、**英文标点转中文标点**。
- 无体裁、朝代、字数等任何派生字段 —— 这些需由 ETL 补齐。

### 1.3 目录组织

两棵树，组织逻辑不同，**不能假设对称**：

- `data/` —— 按**体裁/选集**分目录（`全唐诗/`、`宋词/`、`诗经/`），目录名与文件名混用中英（`poet.tang.json`、`ci.song.json`、`shijing.json`）。
- `data2/` —— 按**朝代**平铺（`元.json`、`明_1.json`…），单一层级。

> **关键发现**：`data2/` **不含唐、宋**（无 `唐.json` / `宋.json`）。上游显然有意用 `data/` 覆盖唐宋。因此跨树重复面很窄，去重压力集中在 `data/` 内部。

## 3. 数据问题

> 以下每条都必须在 ETL 中有明确处置，否则会以脏数据形式漏到客户端。

### 3.1 集合间重复 ★ 影响最大

`data/` 内部多个选集是**同一批诗的不同编纂版本**，实测：

| 关系 | 实测 | 说明 |
|---|---|---|
| 唐诗三百首 ⊂ `poet.tang` | **360 / 366 (98.4%)** | 蘅塘退士选本，诗源即全唐诗 |
| **御定全唐诗 ∩ `poet.tang`** | **19,494 首重复** | 占御定 48.4%；两者并集 76,527（原始合计 96,867） |
| 宋词三百首 ⊂ `ci.song` | 229 / 280 (81.8%) | 命中率低是异文/标点差异所致，实际同源 |
| 水墨唐诗 ⊂ `poet.tang` | 未逐条核，同源推定 | 唐诗选本 |
| 唐诗补录 ⊂ `poet.tang` | 1 首，同源推定 | — |

去重键与合并规则见 §4.2。**这条直接决定"90 万首"最终是多少首**，也决定了数据包怎么切（§6）。

### 3.2 非诗词内容 —— 已决策丢弃

库中混入 **270 条非诗词**：论语(20)、四书五经(16)、蒙学(15)、幽梦影(219)。

**决策：ETL 阶段直接丢弃，不入库。**

理由：这些是语录体与蒙学韵文，与"每日诗词"的产品定位无关；在客户端单独成区会把一个诗词 App 做成国学杂烩。代价是永久丢失这 270 条 —— 但原始数据仍留在 `etl/data_raw/`，上游仓库也随时可重取，故此决策实际可逆。

实现：`etl/mappings/exclude.json` 列出 §2.1 注中那 12 个文件，`parse` 阶段跳过并计入 `etl_report.json` 的 `excluded` 分组。连带影响：`genre` 枚举收窄为 `诗`/`词`/`辞`（§5.3），`合集` 维度不再包含这些书目。

### 3.3 版权 ⚠️ 已知风险

`data2/` 含 20 世纪后作品。按桶统计：

| 朝代桶 | 条数 | 版权判断 |
|---|---|---|
| `近现代` | 28,135 | ⚠️ 高风险 |
| `当代` | 27,943 | ⚠️ 高风险 |
| `近现代末当代初` | 3,376 | ⚠️ 高风险 |
| `民国末当代初` | 1,912 | ⚠️ 高风险 |
| `清末近现代初` | 12,331 | 横跨 1911 边界，部分高风险 |
| `清末民国初` | 15,073 | 横跨 1911 边界，部分高风险 |
| **小计** | **88,770** | 保守上界 |
| 其中可确定为 20 世纪后 | 71,366 | 即 `d2-modern` 包的构成 |

**决策记录：收录全量（含近现代与当代）。**

风险：清及以前属公有领域，无风险；20 世纪后作品的著作权可能仍在保护期，上架 Google Play 或国内应用商店时可能被要求提供授权证明。

**缓解措施**（`poem.is_public_domain BOOLEAN`，ETL 时由 `dynasty_order` 顺带推导，不计额外工作量）：入库时写死，接口默认**不过滤**，保留一个随时可启用的开关，后续若需裁剪无需重跑 ETL。

> ⚠️ **分包边界与版权边界不重合。** `d2-modern`（71,366 首）是明确 20 世纪后的部分，但两个「清末…」桶（27,404 首）横跨 1911，被划入了 `d2-qing`。因此"下架只需摘掉 `d2-modern`"**并不充分** —— 真要合规下架，还需对 `d2-qing` 包按 `is_public_domain` 行级过滤。这是 §6.1 分包方案在此处的已知不完美；在法务要求明确前，v1 不预先处理。

### 3.4 上游已知缺陷

上游 README 自带一份修订记录与完成清单，摘要：

- **元曲已整体排除**（上游说明：内容跑进标题且衔接处有漏字）。故库里没有元曲。
- `御定全唐诗` 已过滤结尾漏句，**中间漏句未处理**。
- `南唐二主词` 淘汰 1 首（《谢新恩·樱花落尽春将困》缺十二字）。
- 繁体未完全消除，生僻字按上游设计**保留繁体**。

ETL 新增处置：

| 问题 | 处置 |
|---|---|
| `唐诗补录.json` 仅 1 首 | 并入 `seed-extra` 包，不单独设包 |
| 生僻字繁体 | **不做二次繁简转换**，避免误伤 |
| 空内容 / 空标题 / 空作者 | 计入 `rejects`，输出报告，不入库 |
| `蒙学/sanzijing-traditional.json` 是繁体，与全库简体规范冲突 | 该文件随 §3.2 整组丢弃，问题自然消解 |

**实测新增的两条上游缺陷**（2026-09-23 构建内置包时发现，未擅改，仅记录）：

| 缺陷 | 实例 | 影响 |
|---|---|---|
| **异文** —— 与通行本不一致 | `唐诗三百首.json` 的《静夜思》为「床前**看**月光…举头望**山**月」（《全唐诗》原貌），而设计稿写的是明代改本「床前明月光…举头望明月」 | ⚠️ **设计稿与实际渲染会对不上**，需产品层面拍板是否改写 |
| **错字** | 《在狱咏蝉》（骆宾王）标题误作《在**岳**咏蝉》 | 标题显示错误 |

两条都不是 ETL 该自作主张修的东西（改文本等于篡改文献），故保持上游原样并在报告中暴露。


### 3.5 上游 `id` 不可直接用

上游 ID 生成规则不统一，README 自述三种：

1. 原生有 ID 的用原生（如全唐诗为 **uuid**）；
2. 有序号的用 `文件名拼音#序号`；
3. 其余用 `文件名拼音#序号`（序号 = 下标 + 1）。

问题：uuid 与 `caocao#1` 混用、无语义、且**跨版本不稳定**（上游重新排序即变）。`poet.tang` / `poet.song` 用 uuid，`data2` 用 `yuan#1` 形式。

处置见 §4.3。

## 4. 领域模型

### 4.1 实体

```
dynasty   朝代（含 period 大期，双粒度）
  └─ author    作者（归一后）
       └─ poem       诗词（唯一实体）
            ├─ collection_member  ←→  collection  合集归属（多对多）
            └─ pack_member        ←→  pack        数据包归属（恰一个）
```

**核心设计：诗词实体与合集归属分离。** 一首诗只存一份正文（`poem`），但它可以同时属于"唐诗三百首"和"御定全唐诗"（`collection_member` 两行）。这样既消了重，又完整保留了"这首诗被哪些选本收录"的信息 —— 而选本本身就是产品的核心浏览入口，不能因为去重而丢失。

### 4.2 去重键与合并规则

**去重键 = `(author_norm, content_norm[:80])`**

- 标题**不参与**键：同一首诗在不同选本中标题常带异文或卷次后缀（《凉州词二首 一》vs《凉州词》）。
- 归一化：
  - `author_norm` —— 去所有空白；剥离括注，如 `李白（唐）` → `李白`；剥离上游残留的 `〖〗`。
  - `content_norm` —— 去所有空白（含全角空格）；去全部中文与英文标点；**不做繁简转换**。
  - 取前 80 字：足以区分绝大多数诗，同时容忍尾联异文。

**合并规则：**

| 字段 | 取值策略 |
|---|---|
| `content` | 取**来源优先级最高**者（优先级见下） |
| `title` | 同上；若优选来源标题含卷次后缀，保留原样 |
| `author` | 同上，写入 `author` 维表 |
| `collection` | **全部保留**（合并为多行 `collection_member`） |
| `pack` | 按来源优先级取最高者（§6.1） |

来源优先级（高 → 低）：`精选集` > `御定全唐诗` > `全唐诗(poet.tang)` > `全唐诗(poet.song)` > `宋词(ci.song)` > `data2/*`

> **同优先级时的决胜规则（实测补充，2026-09-23）**：精选集之间优先级相同，
> 但**内置（L0）包优先**。理由是内置包随 APK 下发，**必须完整**。
>
> 实测踩到过：`唐诗三百首` 与 `水墨唐诗` 同为精选集，有 **51 首**重叠，
> 若按「先遇到者胜」，这 51 首会归入 `seed-extra`，于是内置的 `tang-300`
> 只有 **315 首**而合集实际是 366 首 —— 用户看到「已内置 唐诗三百首」却少了 51 首。
>
> 注意这只影响「诗归哪个下载包」，**合集归属不受影响**：
> 这 51 首依然是《水墨唐诗》的成员（`collection_member` 照旧保留），
> 只是其**离线副本**随内置包一起下发。这正是 §4.1「诗词实体与合集归属分离」的又一次变现。

> 注意实测命中率：宋词三百首对 `ci.song` 只有 81.8%（异文导致）。**这是去重键的固有漏检**，会残留少量重复。可接受 —— 宁可漏去，不可错并（错并会丢诗，不可逆）。ETL 报告须输出各对集合的实测命中率，便于人工复核。

### 4.3 ID 分配

**双层 ID：**

| 字段 | 类型 | 用途 |
|---|---|---|
| `source_id` | TEXT | 保留上游原始 id，用于**溯源**与上游增量比对。唯一索引。 |
| `poem_id` | INTEGER | 系统内主键，**自增但一经分配永不改变**。 |

`poem_id` 的稳定性靠一份纳入版本控制的映射文件 `etl/id_map.jsonl`（`source_id → poem_id`）保证：

- 首次 ETL：按 `source_id` 字典序排序后顺序分配，落盘 `id_map.jsonl`。
- 后续 ETL：先读 `id_map.jsonl`，命中的复用原 `poem_id`；未命中的（新增）追加分配并回写。

不这么做的话，上游任何一次重排都会让全量客户端的本地库与增量包对不上号。`id_map.jsonl` 约 85 万行、~15 MB，用 JSONL 存。

选 INTEGER 而非保留 uuid 字符串，理由：每首省 ~30 字节，90 万首省约 27 MB；且客户端分包、断点续传、按 id 区间校验都更简单。

双粒度（`dynasty` 细分 + `period` 大期）的理由：`data2` 的"明末清初"这类过渡桶与"明""清"并列，若只做单层会导致筛选器里"明"和"明末清初"同级，用户体验割裂。大期用于顶部 Tab，细分用于二级筛选。

> **过渡桶归属约定**：`元末明初` / `明末清初` / `清末…` 这类跨代桶一律归入**较早**的朝代。这样沿 `order` 递增时 `period` 序列是单调的（元→元→明→明→清→清→清→近现代→近现代→近现代→当代），不会出现时间线在两个大期之间来回跳。这是一条必须写进 `mappings/dynasty.json` 的约定，不能靠实现者临场判断。

| `词` | 花间集、南唐二主词、宋词×2、纳兰性德 | 21,069 |

（`纳兰性德诗词.json` 以词为主、含少量诗，此处整体计为 `词`；ETL 可按 `cipai` 提取是否成功做二次细分。）

`赋`/`文`/`蒙学` 已随 §3.2 整组移除，不再需要。若二期引入 `赋`，只需在枚举中加值，不影响 schema。

### 5.4 诗体与词牌

**`form` 推断规则**（仅对 `genre=诗`）：

> ⚠️ **必须先按「句」切分，不能按「行」统计。** 上游的换行粒度是**联**，
> 一行常含两句（`春眠不觉晓，处处闻啼鸟。`）。按行统计则每行都是 10 字，
> 于是一整批五言绝句会被判成「其他」—— 这不是推测，是实测踩到的：
> 内置包初版 366 首唐诗里 **334 首（91%）落进「其他」**。
> 按「，。！？；：、」断句后，「其他」归零，分布为
> 五言律诗 96 / 七言绝句 75 / 七言律诗 56 / 五言绝句 47 / 杂言 28 / 五言古体 26 / 七言古体 21 / 古体 17。

```
verses  = content 按「，。！？；：、」切分（不是按 \n）
lens    = verses.map(去标点去空白后长度)
句长一致 = lens.distinct().size == 1

若 !句长一致           → 杂言
若 句长一致 且 字长 ∈ {5, 7}:
    4 句              → {五,七}言绝句
    8 句              → {五,七}言律诗
    > 8 句            → {五,七}言古体     （对仗判定过于复杂，不尝试排律）
    其他句数          → 古体
若 句长一致 且 字长 ∈ {4, 6} → 四言/六言（诗经、部分古体）
其他                          → 其他
```

预期准确率仍不高（律诗的对仗、拗救无法用句数判定），因此：

> **`form` 定为「尽力而为」字段，客户端不得依赖其准确性做核心功能**，仅用于筛选和展示。ETL 抽样人工核对 200 首，准确率低于 80% 则改为只区分「绝句 / 律诗 / 古体 / 杂言」四类粗粒度。

**`cipai` 提取**（仅 `genre=词`）：

提取规则按可靠性从高到低三条，缺一不可：

1. 标题有分隔符（`·` / 全角空格 / 半角空格）→ 取前段。`菩萨蛮·书江西造口壁` → `菩萨蛮`。
2. 标题无分隔符但**整串命中词牌表** → 整串即词牌。`水调歌头`、`声声慢` 这类标题没有
   任何分隔符，若不做这一步会白白丢掉高价值字段（初版实现正是漏在这里，覆盖率为 0）。
   词牌表来源有二：`COMMON_CIPAI` 内置约 100 条常用词牌；`build_cipai_candidates()`
   从数据推断 —— **短（≤5 字）且重复出现的标题几乎必然是词牌**（词牌是形式名，
   一个词牌下有多位作者；而具体词作的标题不会重复）。
3. 都未命中 → 置 `NULL`。**返回 null 好于猜一个错的词牌**，客户端已正确处理 null。

实测：宋词三百首 280 首中提取成功 **228 首 = 81.4%**。距本文件 §8 要求的 90% 仍差，
缺的是完整词牌词典（约 1,000 条，属 `mappings/cipai.txt`，随全量管线接入）。


`cipai` 是**高价值派生字段**：能支撑"按词牌浏览"这一核心功能，且提取规则简单可靠。

### 5.5 未纳入的字段

`tags` / `theme`（山水、思乡、送别…）：上游无此数据，需 NLP 或人工标注。**v1 不做**，避免引入不可控质量。留作二期，届时以独立表 `poem_tag` 增量叠加，不影响现有 schema。

## 6. 数据分层与打包

### 6.1 分层

| 层 | 门槛 | 说明 |
|---|---|---|
| **L0 内置** | — | 打包进 APK，首启零等待 |
| **L1 小包** | gzip < 3 MB | 可静默下载，不打断用户 |
| **L2 中包** | gzip 3–20 MB | 展示体积，确认后下载 |
| **L3 大包** | gzip > 20 MB | 强制 Wi-Fi + 二次确认 |

**分包原则：包之间互斥。** 每首诗只属于一个包（`pack_member` 恰一行），依据 §4.2 的来源优先级决定归属。合集（`collection`）只是 id 列表，与包正交 —— 内置的"唐诗三百首"合集 id 列表可以指向后续下载的包里的诗。

- **gzip 压缩率按 ~35% 估**（键名逐行重复，gzip 字典命中率极高，实测需校正）。全量下载体积约 **97 MB**。

### 6.2 包格式

**JSONL + gzip**，每行一条：

```json
{"poem_id":1024,"title":"度关山","author":"曹操","dynasty":"汉","period":"秦汉","genre":"诗","form":"杂言","cipai":null,"line_count":16,"char_count":96,"is_public_domain":true,"content":"天地间，人为贵。\n立君牧民，为之轨则。"}
```

两点刻意的设计：

- **不省键名。** 键名逐行重复，gzip 的滑动窗口能把它压到近乎零成本 —— 实测为省几十字节而把字段缩成 `lc`/`cc`/`pd` 得不偿失，可读性和可调试性更值钱。
- **反范式化。** 包内写的是 `author`（作者名）与 `dynasty`/`period`（朝代名），而非服务端的 `author_id`/`dynasty_id`。客户端展示需要名字，为省这点体积让客户端多维护一套维表并做 join 不划算。客户端入库时自行分配本地 `author_id`。

选 JSONL+gzip 而非「服务端直出 SQLite 分片」的理由：

1. **可断点续传** —— HTTP Range 按字节切，天然支持；SQLite 分片断点续传需整文件校验。
2. **体积小** —— gzip 后约为 SQLite 的 1/2（SQLite 页对齐 + 索引开销）。
3. **schema 解耦** —— 客户端 Room 版本升级不必重做全部包。
4. **可流式** —— 边下边解析入库，不必落盘整个文件再处理。

代价是客户端要做 JSON 解析 + 批量插入（250k 行的 `song-shi` 包预计 30–60 秒）。这由前台服务 + 进度通知承载，可接受。**若实测入库超过 90 秒，再退回 SQLite 分片方案** —— 这条留作预案，不在 v1 实现。

**注意换行**：`content` 内的 `\n` 必须转义为 `\\n`，否则会破坏 JSONL 的行结构。这是本格式唯一的实现陷阱。

### 6.3 包元数据

每个包附带 `manifest.json`（也置于服务端 `pack` 表）：

```json
{
  "pack_id": "tang-quanshu",
  "version": 1,
  "name": "全唐诗·唐",
  "tier": "L2",
  "poem_count": 36821,
  "bytes_raw": 12790000,
  "bytes_gzip": 4400000,
  "sha256": "…",
  "min_poem_id": 12000,
  "max_poem_id": 48999,
  "created_at": "2026-09-22T00:00:00Z",
  "requires": [],
  "collections": ["quan-tang-shi"]
}
```

- `sha256` 供客户端**下载后校验**，不通过则丢弃重下。
- `min_poem_id` / `max_poem_id` 供客户端快速判断与已装包是否冲突、支持按 id 区间增量补齐。
- `version` 单调递增，客户端据此判断是否需要更新已装包。

## 7. ETL 管线

### 7.1 阶段

```
fetch  →  parse  →  normalize  →  derive  →  dedup  →  assign_id  →  load  →  pack  →  verify
```

| 阶段 | 输入 | 输出 | 备注 |
|---|---|---|---|
| `fetch` | 上游 URL 清单 | `data_raw/*.json` | 幂等：已存在且 sha256 匹配则跳过 |
| `parse` | `data_raw/` | `RawPoem` 流 | 记录每个源文件的条数，与 §2 清单比对 |
| `normalize` | `RawPoem` | `NormPoem` | 空白/标点归一、字段 trim、`rejects` 收集 |
| `derive` | `NormPoem` | `+ 派生字段` | 查 §5.2/§5.3 映射表 |
| `dedup` | `NormPoem` 流 | 唯一 `Poem` + `collection_member` | 内存哈希表，85 万条约 300 MB 内存，单机可行 |
| `assign_id` | 唯一 `Poem` | `+ poem_id` | 读 `id_map.jsonl`，未命中则追加 |
| `load` | `Poem` | `poems.db` | 批量 insert，含 FTS5 建索引 |
| `pack` | `poems.db` | `packs/*.jsonl.gz` + `manifest.json` | 按 §6.1 分区 |
| `verify` | 全部产物 | `etl_report.json` | 见 §8 |

### 7.2 工程约束

- **幂等**：每阶段独立可重跑，中间产物落盘。改分包规则时只需重跑 `pack`，不必重下 283 MB。
- **稳定**：`etl/id_map.jsonl` 与 `packs/*/manifest.json` **纳入版本控制**。这是增量一致性的唯一依据。
- **内存**：`dedup` 阶段需一次装入全部去重键（约 85 万 × ~350 字节 ≈ 300 MB）。若内存吃紧，改为按 `dynasty` 分桶两趟合并 —— 因为重复只发生在同朝代内（已实测跨树无唐宋重叠）。
- **语言**：Python 3.13（本机已装）。仅需标准库 + `jieba`（若 FTS5 需中文分词，见 03 §FTS）。

### 7.3 目录结构

```
etl/
  fetch.py          ★ 拉取上游（幂等 + Range 续传）
  run_etl.py        ★ 编排入口（--from / --only / --no-fts）
  lib/
    sources.py?     —— 已合并进 mappings/sources.json，见下
    text.py         归一与派生（去重键 / char_count / form / cipai）
    ids.py          IdAllocator：source_id → poem_id 的持久映射
    schema.py       poems.db 的 DDL（与 docs/03 §2.2 同源）
    pipeline.py     ★ 九个阶段的实现（parse / derive / dedup / assign / load / pack / verify）
  mappings/
    sources.json    ★ 唯一真相源：36 个源文件 × 朝代/体裁/权重/优先级/包归属
    builtin_sets.json  仅内置（L0）包的定义，供 build_builtin_packs.py 用
    exclude.json    §3.2 的 12 个排除文件
  id_map.jsonl      ★ 纳入版本控制
  fetch_state.json  下载偏移（可删，重下即可）
  data_raw/         gitignore
  build/            gitignore（中间产物 + etl_report.json）
```

**与本节初版的两处收敛**（实现时改的，理由如下）：

1. **五个 mappings 文件合并为 `sources.json`。**
   初版把朝代、体裁、来源优先级、包归属拆成 `dynasty.json` / `genre.json` /
   `source_priority.json` / `exclude.json` 等多份。但这四者**逐源一一对应** ——
   每个源文件恰有一个朝代、一个体裁、一个优先级、一个包。拆开只会产生
   「改了朝代忘了改包」这类跨文件不一致，合并后每行自洽、一处可查。
2. **九个阶段不拆成九个可执行文件，而是 `lib/pipeline.py` 里九个同名函数 + `run_etl.py` 编排。**
   阶段名与职责与 §7.1 完全一致，仍可单独调用与单测；
   拆成九个只跑一次的小脚本，收益仅是文件数变多。

**中间产物只落两份**（`build/parsed.jsonl`、`build/derived.jsonl`）而不是每阶段一份：
85.9 万首的 JSONL 每份约 300 MB，九份就是 2.7 GB，而 §7.2 要的「改分包规则不必重下
283 MB」这一目标，切点在 `derived` 就足够了。

## 8. 验收标准

ETL 结束后 `etl_report.json` 必须给出以下数据，且全部通过方可发布：

| 检查项 | 阈值 |
|---|---|
| 各源文件解析条数 | 与 §2.1/§2.2 清单**逐文件**一致（±0） |
| 排除文件数 | `excluded` 恰为 12 文件 / 270 条（§3.2） |
| 去重后唯一诗词数 | 落在 830,000 – 860,000 之间，且报告给出精确值 |
| `genre` 枚举 | 仅出现 `诗`/`词`/`辞` 三值，无 `文`/`蒙学` 残留 |
| 去重键碰撞抽查 | 随机抽 200 组判定为同诗者，人工复核误并率 **< 1%** |
| `poem_id` 稳定性 | 重跑 ETL 后 `poem_id` 无变化（全量 diff 为空） |
| 空/残缺字段 | `title`/`content`/`author` 非空率 100%；原缺作者者标记 `作者待考` |
| `form` 抽样准确率 | 人工核 200 首，**≥ 80%**；否则降级为粗粒度四分类 |
| `cipai` 覆盖率 | `genre=词` 中成功提取率 **≥ 90%** |
| 包完整性 | 恰 **12 个包**（§6.1）；各包 `poem_count` 之和 == 唯一总数；无跨包重复 `poem_id` |
| 包体积 | 全量 gzip 后 **< 120 MB** |
| 包校验 | 逐包 gzip 解压 + sha256 比对通过 |
| 客户端冒烟 | 用 `seed` 包在真机冷启动，1 秒内出诗 |

## 9. 决策记录

设计过程中已拍板的项，连同理由记录于此以便回溯：

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据收录范围 | **全量**（含近现代/当代） | 覆盖最全；版权风险由 `is_public_domain` 字段留后路（§3.3） |
| `御定全唐诗` 与 `poet.tang` 的重复部分 | **两者均保留** | 互有独家（御定独占 21,058、poet.tang 独占 36,821），且属不同编纂体系，有版本学价值 |
| 270 条非诗词 | **直接丢弃** | 与"每日诗词"定位无关，独立成区会稀释产品（§3.2） |

## 10. 遗留问题

1. **`form` 推断准确率需实测** —— §5.4 的降级预案是否启用，要等数据说话。
2. **§6.1 的包首数与体积是全文唯一的估算项**（按 330 B/首原始、115 B/首 gzip 折算），须由 ETL 产出精确值后回填。§2 的清单与 §3.1 的重复率均为实测。
3. **`御定全唐诗` 独占的 21,058 首含上游未处理的中间漏句**（§3.4），长诗在客户端可能出现语义断裂。二期是否做人工校勘，待抽样评估后再定。
4. §1.3 提到 `data/` 目录名与文件名中英混用，ETL 的 `mappings/` 必须按**文件路径**（而非目录名）建表，否则 `poet.song.json`（宋诗，在"全唐诗"目录下）会被误判为唐诗。
