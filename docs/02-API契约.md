# 02 · API 契约

> 本文定义前后端的**唯一分界**。客户端不假设服务端的存储结构，服务端不假设客户端的渲染方式，双方只依赖本文的端点与数据对象。
> 设计原则：**从功能倒推接口**，不做预留式设计。无账号、无社交、无推荐，对应地 API 里就没有这些资源。

---

## 1. 总览

### 1.1 基础约定

| 项 | 值 |
|---|---|
| Base URL | `https://<host>/api/v1` |
| 传输 | HTTPS，JSON（`Content-Type: application/json; charset=utf-8`） |
| 鉴权 | **无**（本项目无账号体系，见 §6.2） |
| 时间 | ISO 8601 UTC，如 `2026-09-22T00:00:03Z`；纯日期用 `YYYY-MM-DD` |
| 字符 | 全部 UTF-8；`content` 内的换行是 `\n`（真实换行，非转义的 `\\n`——后者仅存在于 §01 §6.2 的 JSONL 包里） |

### 1.2 资源总览

只有 11 个端点。对照 `01` 的功能清单，**浏览类需求全部收敛到 `/poems` 一张查询表** —— "朝代=唐""合集=唐诗三百首""词牌=菩萨蛮""作者=李白"都只是筛选参数，不是独立资源。`/daily/batch` 是为客户端预取单开的，与 `/daily` 职责分离。最后两个端点是 `06-注释与赏析.md` 引入的：注疏是独立库（`annotations.db`），问答是流式（SSE），都不是 `poem` 的附属字段那么简单。

| 端点 | 功能 | 可离线满足 |
|---|---|---|
| `GET /daily` | 每日一诗（单日） | ⚠️ 部分（见 §5.3） |
| `GET /daily/batch` | 每日一诗批量预取 | ⚠️ 部分（见 §5.3） |
| `GET /poems` | 列表查询（万能筛选） | ✅ 取决于包 |
| `GET /poems/{id}` | 诗词详情（含注疏，见 `06`） | ✅ 取决于包 + 注疏缓存 |
| `GET /poems/random` | 随机漫游 | ✅ 取决于包 |
| `GET /search` | 搜索 | ✅ 取决于包 |
| `GET /facets` | 筛选器元数据 | ✅ 缓存后 |
| `GET /authors/{id}` | 作者信息 | ✅ 缓存后 |
| `GET /packs` | 离线包清单 | ❌ 必须联网 |
| `GET /poems/{id}/annotation` | 注疏读取（`06`） | ✅ 缓存后 |
| `POST /poems/{id}/ask` | 就某首诗提问（**SSE 流式**，`06`） | ❌ 必须联网 |

### 1.3 分页

统一游标（keyset）分页，不用 offset —— 全量 85.9 万首下深翻页 offset 会线性退化。

```
?cursor=<opaque>&limit=20
```

- `limit` 默认 20，上限 100。
- `cursor` 为不透明字符串，客户端**只回传不解析**。
- 响应中 `next_cursor` 为 `null` 表示没有下一页。
- `sort` 变化时游标失效，客户端应丢弃旧游标重新开始。

### 1.4 错误

```json
{ "error": { "code": "POEM_NOT_FOUND", "message": "poem_id 999999 不存在" } }
```

| code | HTTP | 触发条件 |
|---|---|---|
| `INVALID_PARAM` | 400 | 参数缺失或格式错（如 `q` 为空、日期非法） |
| `POEM_NOT_FOUND` | 404 | `poem_id` 不存在 |
| `AUTHOR_NOT_FOUND` | 404 | `author_id` 不存在 |
| `PACK_NOT_FOUND` | 404 | `pack_id` 不存在 |
| `RATE_LIMITED` | 429 | 触发限流 |
| `INTERNAL` | 500 | 服务端异常 |

`message` 仅供开发期排查，**客户端不得依赖其内容**，一律按 `code` 分支。

## 2. 数据对象

### 2.1 `PoemSummary`（列表用）

```json
{
  "poem_id": 1024,
  "title": "度关山",
  "author": "曹操",
  "dynasty": "汉",
  "genre": "诗",
  "excerpt": "天地间，人为贵。"
}
```

`excerpt` = 正文第一行。列表 UI 只需要这一句就能让用户判断是否点开，返回全文属于浪费。**详情页才给全文。**

### 2.2 `PoemDetail`

```json
{
  "poem_id": 1024,
  "title": "度关山",
  "author": { "author_id": 88, "name": "曹操", "dynasty": "汉" },
  "dynasty": "汉",
  "period": "秦汉",
  "genre": "诗",
  "form": "杂言",
  "cipai": null,
  "content": "天地间，人为贵。\n立君牧民，为之轨则。\n…",
  "line_count": 16,
  "char_count": 96,
  "is_public_domain": true,
  "collections": [
    { "slug": "caocao-shiji", "name": "曹操诗集" }
  ],
  "annotation": null,
  "translation": null,
  "appreciation": null,
  "annotation_background": null,
  "annotation_citation": null,
  "annotation_sources": []
}
```

五点说明：

- **`collections` 是详情页的一个功能亮点。** 因为 `01 §4.1` 把诗词实体与合集归属分离了，这里能直接告诉用户"这首诗收录于《唐诗三百首》"——这是选本类 App 的核心信息，去重时特意保住的。最多返回 5 个，按合集权重排序。
- **注疏字段自 `06` 起开始填充，但 `null` 仍是长期常态。** 全量 83.4 万首里只有 7,388 首有注疏（占 0.88%，`06 §2.4`）。**客户端必须容忍 null 并隐藏区块，不得渲染空标题** —— 而且**不得把「没有注疏」表述成「加载失败」**：那是常态，说成失败会让用户以为 App 坏了。正确答案是引导用户去提问（`POST /poems/{id}/ask`）。
- **`annotation` 是扁平字符串**，逐条注释按「词：义」一行一条（`06 §5.1`）。**不是结构化数组** —— 契约里它就是字符串，改成数组是破坏性变更，而上游本身就是这个形态。
- **`annotation_background` / `annotation_citation` / `annotation_sources` 是新增可选字段**（`§7`：向后兼容的加法不升版本）。`background` 是创作背景（史实，与赏析的评论性质不同，故单列）；`citation` 是文献出处（如「王运熙 等．唐诗鉴赏辞典．上海：上海辞书出版社，1983：46-47」）；`sources` 指向古诗文网站内检索页。三者都是**「内容有据可查」的凭据**，客户端应展示而非忽略（`06 §7`）。
- `form` 是尽力而为字段（`01 §5.4`），客户端仅可用于展示与筛选，**不得用于核心逻辑分支**。

### 2.3 `SearchHit`

```json
{
  "poem_id": 1024,
  "title": "滕王阁序",
  "author": "王勃",
  "dynasty": "唐",
  "hit": "content",
  "snippet": "落霞与孤鹜齐飞，秋水共长天一色。",
  "highlights": [[0, 9]]
}
```

`highlights` 是 `snippet` 内的**字符区间**（左闭右开），供客户端做富文本高亮。

**为什么返回区间而不是 `<em>` 标记串**：标记串要客户端解析 HTML，且一旦用户搜索内容含 `<` 就可能出问题；区间是纯数据，客户端用 `AnnotatedString` 直接渲染，零解析、零注入面。

`hit` 取值 `title` / `author` / `content`，用于客户端排序与展示"命中标题"标识。

## 3. 端点

### 3.1 `GET /daily` — 每日一诗

| 参数 | 必填 | 说明 |
|---|---|---|
| `date` | 否 | `YYYY-MM-DD`。默认今天。**支持过去 365 天与未来 90 天** |

```json
{
  "date": "2026-09-22",
  "poem": { "...PoemDetail" },
  "pool_size": 859591
}
```

- 响应头带 `Cache-Control: public, max-age=<距当日 24:00 的秒数>`，客户端当天只需请求一次。
- 诗由服务端**定时任务每日 00:00 预生成**并落 `daily_pick` 表，接口只读该表。选诗逻辑见 §4。
- `pool_size` 暴露当前候选池大小，用于诊断"为什么某天的诗很冷门"这类问题。- **日期窗口**：定时任务维护一个滚动窗口 `[今天-365, 今天+90]`。窗口内任意日期均可查（含未来，供客户端预取）；窗口外返回 `INVALID_PARAM`。
- 批量预取走 `GET /daily/batch`（§3.2），**不要循环调用本端点 30 次**。

### 3.2 `GET /daily/batch` — 每日一诗批量预取

客户端预取用（§4.2）。

| 参数 | 必填 | 说明 |
|---|---|---|
| `from` | 否 | `YYYY-MM-DD`，默认今天 |
| `days` | 否 | 1–30，默认 30 |

```json
{
  "items": [
    { "date": "2026-09-22", "poem": { "...PoemDetail" } },
    { "date": "2026-09-23", "poem": { "...PoemDetail" } }
  ]
}
```

- 单次上限 30 天。超出窗口的日期**从结果中静默跳过**，不报错 —— 预取是尽力而为，不应因边界日期让整批失败。
- 客户端应缓存全部 `items`，这是离线可读性的来源（§5.3）。

### 3.3 `GET /poems` — 列表查询

万能筛选端点。参数全部可选，可组合：

| 参数 | 取值 | 说明 |
|---|---|---|
| `period` | 大期 key，如 `suitangwudai` | 顶部 Tab 用 |
| `dynasty` | 细分，如 `tang` | 二级筛选用 |
| `genre` | `shi` / `ci` / `ci_sao` | 诗/词/辞 |
| `cipai` | 词牌名，如 `菩萨蛮` | 仅 `genre=ci` 有意义 |
| `author_id` | 整数 | 作者作品列表 |
| `collection` | 合集 slug，如 `tangshi-sanbai` | 选本浏览 |
| `form` | 如 `wuyan-jueju` | 诗体筛选（准确性有限） |
| `sort` | `weight`（默认）/ `id` / `dynasty` | |
| `cursor` / `limit` | | §1.3 |

```json
{
  "items": [ { "...PoemSummary" } ],
  "next_cursor": "eyJ...",
  "total": 56315,
  "applied_filters": { "dynasty": "tang" }
}
```

**`sort` 默认 `weight` 而非 `id`** —— 这是本设计中的重要一条。入库 85.9 万首，但用户不可能浏览 25 万首宋诗；这类产品的价值在**精选发现**。按 `weight` 排序使唐诗三百首、宋词三百首等选本成员浮到前面，冷门诗只在精确搜索/随机时出现。`weight` 由 ETL 按来源合集计算（`01 §5.1`）。

`applied_filters` 回显服务端实际生效的筛选，便于排查"我传了参数却没过滤"这类问题（例如传了 `cipai` 但 `genre` 不是 `ci`）。

### 3.4 `GET /poems/{id}` — 详情

返回 `PoemDetail`。无参数。

### 3.5 `GET /poems/random` — 随机漫游

接受与 §3.3 **相同的筛选参数**（`sort` / `cursor` / `limit` 除外），返回 `PoemDetail`。

`?dynasty=tang` 即"随机来一首唐诗"。**离线时客户端本地随机**，不调此端点（§5.2）。

### 3.6 `GET /search` — 搜索

| 参数 | 必填 | 说明 |
|---|---|---|
| `q` | **是** | 查询串，1–64 字。空或超长返回 `INVALID_PARAM` |
| `scope` | 否 | `all`（默认）/ `title` / `author` / `content` |
| `cursor` / `limit` | | §1.3 |

```json
{
  "items": [ { "...SearchHit" } ],
  "next_cursor": null,
  "total": 37,
  "query": "落霞与孤鹜齐飞"
}
```

**核心场景是"记得一句诗，找全诗"** —— 这是诗词类 App 最高频的搜索用法。因此：

1. **索引按句粒度建，而非整首当一坨文本。** 这样才能高亮到具体那一句，并让用户一眼看到命中上下文。
2. **排序：标题精确命中 > 作者命中 > 正文命中；同类型内按 `weight` 降序。** 用户搜"李白"时，想要的是李白的代表作，不是按 id 排的第一万首。
3. `snippet` 取命中句及其前后各一句，总长控制在约 60 字。

分词用 jieba（`01 §7.2`）。`q` 若为纯作者名，`scope=author` 可显著提速。

### 3.7 `GET /facets` — 筛选器元数据

客户端启动时拉一次并长期缓存，用于渲染各种筛选面板。

```json
{
  "periods": [
    { "key": "xianqin", "name": "先秦", "count": 370 },
    { "key": "suitangwudai", "name": "隋唐五代", "count": 99097 }
  ],
  "dynasties": [
    { "key": "tang", "name": "唐", "period": "suitangwudai", "count": 97410 }
  ],
  "genres": [
    { "key": "shi", "name": "诗", "count": 838457 },
    { "key": "ci", "name": "词", "count": 21069 },
    { "key": "ci_sao", "name": "辞", "count": 65 }
  ],
  "cipais": [
    { "name": "菩萨蛮", "count": 638 }
  ],
  "collections": [
    { "slug": "tangshi-sanbai", "name": "唐诗三百首", "count": 366, "builtin": true }
  ],
  "generated_at": "2026-09-22T00:00:00Z"
}
```

> 上例中的 `count` 为**去重前的原始条数**（唐 = poet.tang 56,315 + 御定 40,552 + 三百首 366 + 水墨 176 + 补录 1 = 97,410），与 `01 §2` 清单一致。实现时若改用去重后计数，需同步更新 `01` 的验收标准。`cipais` 的计数为示意值。

- `dynasties[].period` 让客户端无需硬编码就能渲染"大期 → 细分"的两级筛选，**层级关系完全由服务端驱动**，`01 §5.2` 的映射表是唯一真相源。
- `collections[].builtin` 标记该合集是否在 `seed` 内置包内 —— 客户端据此决定显示"已内置"还是"需下载"。
- 全部词牌约 1,000 条（~40 KB），一次性返回，`Cache-Control: max-age=86400`。

### 3.8 `GET /authors/{id}` — 作者

```json
{
  "author_id": 88,
  "name": "曹操",
  "dynasty": "汉",
  "poem_count": 26
}
```

作品列表走 `GET /poems?author_id=88`。`name` 可能为 `作者待考`（`01 §8`），客户端应正常展示而非当作错误。

> ⚠️ **`author_id` 不可离线使用。** 它是服务端分配的（`03 §2.2`），而离线数据包里只有作者**名**（`01 §6.2` 的包格式不含 `author_id`）。客户端因此必须**按归一化后的作者名**建立本地作者索引。
>
> 这不构成不一致：服务端的 `author_id` 本就按归一化作者名分组（`01 §4.2` 剥离 `李白（唐）` → `李白`），而包里写的也是归一化后的名字。故 `WHERE author = '李白'` 与 `?author_id=88` 返回**同一组诗**。**本地导航键是作者名，`author_id` 仅用于在线调 `/authors/{id}`。**

### 3.9 `GET /packs` — 离线包清单

```json
{
  "catalog_version": 3,
  "packs": [
    {
      "pack_id": "tang-quanshu",
      "name": "全唐诗·唐",
      "tier": "L2",
      "version": 1,
      "poem_count": 36821,
      "bytes_gzip": 4400000,
      "sha256": "…",
      "min_poem_id": 12000,
      "max_poem_id": 48999,
      "builtin": false,
      "collections": ["quan-tang-shi"],
      "download_url": "https://<cdn>/packs/tang-quanshu.v1.jsonl.gz"
    }
  ]
}
```

- `catalog_version` 单调递增。客户端存下它，下次请求带 `If-None-Match` 或直接比对，未变则跳过。
- **`download_url` 指向静态文件，不经过 API 服务。** 包是 4–29 MB 的不可变文件，交给 nginx/CDN 直接吐，API 服务不承担大文件带宽。`sha256` 供客户端下载后校验。
- 清单本身的字段定义见 `01 §6.3`。

### 3.10 `GET /poems/{id}/annotation` — 注疏读取

注疏的**独立读取端点**（设计见 `06-注释与赏析.md`）。为什么不复用 `/poems/{id}`：
后者要 join 作者/朝代/合集三张表，而这里只查注疏库一张 PK 表。

```json
{
  "poem_id": 2,
  "status": "ready",
  "annotation": "幽州：古十二州之一，现今北京市。\n幽州台：即黄金台…",
  "translation": "往前不见古代礼贤下士的圣君…",
  "appreciation": "诗人具有政治见识和政治才能…",
  "background": "这首诗写于公元696年（武则天万岁通天元年）…",
  "citation": "王运熙 等．唐诗鉴赏辞典．上海：上海辞书出版社，1983：46-47",
  "sources": [ { "title": "古诗文网（CC0-1.0）", "url": "https://so.gushiwen.cn/search.aspx?value=登幽州台歌" } ],
  "source": "gushiwen",
  "license": "CC0-1.0"
}
```

**只有两个 `status`**：

| `status` | 含义 | 客户端该做什么 |
|---|---|---|
| `ready` | 已收录 | 展示注疏区块 |
| `missing` | 未收录 | **不说「加载失败」**，而是提示可在本页提问（§3.11） |

**没有「生成中 / 已排队 / 失败」这些状态** —— 注疏是预先从网络导入的真人编辑内容
（`06 §1`），不需要等，也没有生成这回事。未知 `status` 一律按 `missing` 处理。

**`source` / `license` 必须回传**：这张库装的是别人的编辑成果，
它们是「这条内容从哪来、能不能商用」的凭据（`06 §7`），不是可选装饰。

**不校验 `poem_id` 是否存在**：只查注疏库一次，为报 404 多查一次诗词库不划算；
客户端拿不到时会自然去走 `/poems/{id}`。

### 3.11 `POST /poems/{id}/ask` — 就某首诗提问（**SSE 流式**）

方式一。这是**本项目唯一的流式端点**，响应是 `text/event-stream` 而不是 JSON。

请求：

```json
{ "question": "「怆然」怎么读？是什么意思？", "search": true }
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `question` | 是 | 1–200 字（上限 `SHICI_ASK_MAX_QUESTION_CHARS`），空或超长返 `INVALID_PARAM` |
| `search` | 否 | 是否先检索；不传取服务端配置（默认开）。`false` 可用于快速模式或调试 |

响应（`Content-Type: text/event-stream`）：

```
event: sources
data: {"items":[{"title":"…","url":"…"}],"searched":true}

event: delta
data: {"text":"幽"}

event: done
data: {"ok":true}
```

- **`sources` 一定先于第一个 `delta` 到达** —— 客户端要能在第一个字出现之前
  就把「正在查资料」换成「参考了这几页」。
- **`delta` 是增量文本**（1–3 个汉字一段），客户端**累加渲染**。
- 失败给 `event: error` + `{"message":"…"}`。**异常不体现为 HTTP 500** ——
  流已开始（状态码早已发出 200），只能靠事件通道上报。**流中途失败时已吐出的文本仍然有效**，
  客户端不应清空它（用户已经读到的半句不该凭空消失）。
- ⚠️ 响应头带 `X-Accel-Buffering: no`。反代常默认缓冲整段响应，
  那会把流式变成「憋几十秒再一次性吐出」。
- **校验 `poem_id` 存在**（404）：问答要把诗的正文拼进提示词，
  没有上下文就不该让模型凭空回答。这是本端点必须比 §3.10 多做一次校验的原因。
- **不落库**：问答是针对某个具体问题的回答，不是对整首诗的系统注疏
  （`06 §1`）。把它当注疏缓存会让「这首诗有没有注疏」含义模糊。
- 延迟参考（本地 9B 模型）：首字约 2 s，短答约 13 s、长答约 33 s（`06 §6.3`）。

## 4. 每日一诗的选诗规则

**服务端选诗是主路径，客户端本地选诗只是兜底机制。两者不做一致性要求** —— 它们服务的目标不同：服务端要的是**可操作性**（人工干预、主题策划、权重调节），客户端要的只是**断网时别开天窗**。强行让两端算出同一首诗，只会把两边的池子和算法同时锁死。

### 4.1 服务端选诗（主路径）

定时任务维护一个滚动窗口 `[今天-365, 今天+90]`（与 §3.1 一致）：每日 00:00 向前补生成 1 天，窗口内每一天都有确定的 `daily_pick` 记录；`/daily` 只读该表，从不临时计算。

**候选池即入库全量，`weight` 只控制相对概率，不控制池子边界。** 分层依据**唯一来自合集归属**（`01 §5.1`）：

| 层 | 判据 | 合集 | 首数 |
|---|---|---|---|
| W3 | **选本** —— 从数万首中挑出数百首，强编辑信号 | 唐诗三百首 366、宋词三百首 280、水墨唐诗 176 | 822 |
| W2 | **全收型经典** —— 整个作品皆为名篇，无需筛选 | 诗经 305、花间集 497、纳兰性德 258、楚辞 65、南唐二主词 44、曹操诗集 26 | 1,195 |
| W1 | **全集** —— 总集或无合集归属，收录即入库 | 御定全唐诗 40,552、`poet.tang` 56,315、`poet.song` 250,351、`ci.song` 19,990、唐诗补录 1、`data2/*` 全部 490,365 | 857,574 |
| | | **合计** | **859,591** |

> **`weight` 不是原数据字段，是我们造出来的。** 上游记录只有 `id` / `title` / `author` / `content`（`01 §1.2`），没有热度、评分、收录次数等任何可用信号。**唯一可用的信号是 `collection_member`** —— 这也是 `01 §4.1` 去重时特意保留合集归属的第二次变现。

**默认池 = 全量 859,591 首**（`DAILY_POOL_MIN_WEIGHT` 默认 `W1`，即不排除任何层）。配置项可收紧到只留 W2 或 W3。

加权随机：W3 概率最高，W1 的冷门诗偶有一首 —— 对"每日一诗"这种产品，**偶尔来一首深度冷门是惊喜而非事故**，前提是权重正确。建议初值 `W3=100 / W2=30 / W1=1`，实现时调参（见 §9）。

> ⚠️ **W1 档内部 `weight` 无区分能力。** 85.7 万首权重完全相同，加权随机落到 W1 时，实际是均匀抽取。这不是实现缺陷，而是**现有数据的信号上限**：真正浮得上来的只有 W3 + W2 那 2,017 首。字数/行数与质量无关；作者作品数是**反向指标**（乾隆四万余首，绝大多数平庸）。若要让 W1 也有真实排序，须引入外部清单（如部编版语文教材必背篇目、王兆鹏《唐诗排行榜》），列入二期可选，见 §9。

**为什么池子可以开到全量**：`/daily` 返回的是**完整 `PoemDetail`**，客户端连正文一起缓存（§4.2）。所以选中的诗是否在用户本地包里，**不影响离线可读性** —— 这一点由缓存保证，不靠限制池子。

规则：

| 规则 | 值 |
|---|---|
| 重复窗口 | 同一首诗 **365 天**内不重复 |
| 权重 | 按 `weight` 加权随机，名篇概率更高 |
| 人工干预 | **支持预置指定日期的指定诗**（节日、节气主题）——池子大才能真正用起来，中秋可挑任意咏月诗 |
| 可追溯 | `daily_pick` 留档，事后可知某天推了什么 |

选诗本身可用确定性算法（`hash(date + salt) % 池大小`，配合不重复窗口），但 `daily_pick` 表仍保留 —— 因为**人工干预**与**可追溯**这两点无法由确定性算法提供。

### 4.2 客户端缓存（保证离线可读的关键）

客户端在有网时**预取未来 30 天的每日一诗，连正文一起存**。

`PoemDetail` 每条约 1 KB，30 天约 30 KB —— 代价可忽略，效果是**用户断网一个月仍有新诗可看**，且与下载了哪些数据包完全无关。这是主路径能在离线场景下成立的根本原因。

### 4.3 客户端本地选诗（兜底）

仅当**缓存耗尽 且 无网络**时触发，是末位机制：

- 池子 = **本地已下载的全部内容**（`seed` 内置包保底 1,192 首，用户下载了更多包则自动变大）。
- 算法用本地随机即可，**无需与服务端一致**。
- UI 明确标注"离线精选"，让用户知道这不是当天的服务端推荐。

池子大小随在线状态变化的本质就是这一条：**在线时池子由服务端决定（可达全量），离线时池子等于用户手里的数据。**

## 5. 跨切面：离线等价性 ★

这是本契约最重要的一节。App 的形态是"**本地优先**"：用户下载了数据包后，绝大多数功能应当完全离线可用。这要求**同一个查询，服务端与本地能给出等价结果**。

### 5.1 两端必须语义一致的部分

以下筛选的语义在服务端 SQL 与客户端 Room 查询中**必须逐字一致**，否则同一操作在有网/无网时结果不同，是极难排查的 bug 来源：

| 项 | 一致性要求 |
|---|---|
| `sort=weight` 的**主排序键** | `weight DESC`。权重相同的诗，两端都必须有**确定性的次级排序**（`poem_id ASC`），否则顺序不稳定 |
| `dynasty` / `period` 映射 | 客户端从 `/facets` 取，不硬编码 |
| `genre` 枚举 | 同上 |
| 搜索的**粗排序** | 标题命中 > 作者命中 > 正文命中；每一档内按 `weight DESC` |
| 游标语义 | 客户端本地分页不必用游标，但**每页边界必须与 `weight` 排序一致** |

**搜索不承诺跨端的精确顺序。** 有网时结果来自服务端（FTS5 + BM25，`03 §4.3`），无网时来自本地 `LIKE`（`04 §6`）——两者的**档内相对顺序本来就不同**，强行对齐意味着客户端也要引入 jieba 分词与倒排索引，代价远超收益。

**覆盖范围也不同，这是能力边界而非不一致**：在线搜全量 859,591 首，离线只搜已下载内容（`04 §6.3`）。离线时必须 UI 明示，让用户知道"搜不到"是因为没下载，而不是 App 坏了。

因此契约只保证**粗排序一致**：标题命中一定排在正文命中前面，每一档内一定按 `weight` 降序。**同一档内两首权重相同的诗谁先谁后，不保证也不应保证** —— 用户对这一层的顺序无感知。这是显式放宽，不是遗漏。

### 5.2 各端点的离线策略

| 端点 | 离线行为 |
|---|---|
| `/poems` | 本地 Room 查询。若筛选结果的包未下载，**明确提示"该内容未下载"并给下载入口**，不得静默返回空列表 |
| `/poems/{id}` | 本地查询；未下载则提示 |
| `/poems/random` | 本地随机（在已下载集合内） |
| `/search` | **有网走本端点；无网回退本地 `LIKE`**（不建 FTS，见 `04 §6`）。离线时未下载部分搜不到 —— **需在 UI 明示"仅在已下载内容中搜索"** |
| `/facets` | 用缓存；首次启动无缓存则用 `seed` 包的本地统计 |
| `/daily` | 见 §5.3 |
| `/packs` | 必须联网 |
| `GET /poems/{id}/annotation` | 读客户端本地注疏缓存（Room `poem_annotation` 表）；未缓存过则视为 `missing` |
| `POST /poems/{id}/ask` | **必须联网**。离线时客户端**不给提问入口**，而提示「联网后可提问」 |

**"未下载"必须是一个显式 UI 状态**，不能表现为"没有结果"。用户搜不到一首诗，会认为是 bug；告诉他"这部分内容还没下载"，他才知道该做什么。

### 5.3 每日一诗的离线回退

因为 `/daily` 返回完整 `PoemDetail`，客户端**连正文一起缓存未来 30 天**（§4.2），所以离线可读**不依赖**用户下载了哪些包。三级降级：

1. 当天有网 → `/daily`，服务端选诗（主路径）
2. 当天无网但缓存命中 → 读缓存，**与在线体验完全一致**（含正文与合集信息）
3. 缓存耗尽且无网 → 本地在已下载内容中随机选一首，标注"离线精选"（§4.3）

第 3 级是末位机制，与服务端结果**不做一致性要求**，也不应尝试对齐 —— 强行对齐会把服务端的池子和算法一并锁死（§4）。

## 6. 明确不做的事

主动划出边界，避免范围蔓延。

### 6.1 接口里没有的资源

| 不做 | 原因 |
|---|---|
| 注册 / 登录 / token | 无账号体系 |
| 收藏 / 取消收藏 / 收藏列表 | **完全本地存储**（Room），服务端不参与，故无端点 |
| 阅读历史 / 进度同步 | 同上 |
| 评论 / 点赞 / 分享计数 | 无社交 |
| 个性化推荐 | 无账号即无个性化，且冷启动数据不足 |
| 数据上报 / 埋点 | 不在本期范围 |

### 6.2 收藏与历史的预留

收藏、阅读历史全部存本地，**服务端不存、不传**。代价是换设备会丢，收益是省掉整个账号体系（注册/登录/密码找回/JWT 刷新/隐私政策/用户数据合规）。

客户端 Room schema 预留 `user_id` 与 `synced_at` 两个字段（默认 `NULL`），二期若加账号同步**不需要改表**。这是**客户端**的事，API 契约不受影响。

### 6.3 注释/译文/赏析

**已实现**，设计文档见 **`06-注释与赏析.md`**。

关键是理解这里有**两条互不替代的路**（`06 §1`）：

| | 方式一 | 方式二 |
|---|---|---|
| | `POST /poems/{id}/ask`（流式问答） | `GET /poems/{id}/annotation` + `PoemDetail` 的注疏字段 |
| 内容 | 模型现场作答 | **从网络导入的真人注疏** |
| 覆盖 | 任意一首 | 7,388 首（0.88%） |
| 落库 | 否 | 是（`annotations.db`） |

**务必记住这三条：**

1. **注疏是真人编辑内容，不是模型生成的。** 曾走过一段弯路：让 LLM 批量生成注释 JSON
   —— 结果不可靠（实测把「怆然」的读音答成 `chuáng rán`，而同一段回答的前半句又写着
   `chuàng`）、无法流式、单首 30–60 s。这条路已被否决，不要在它上面继续加东西。
2. **`null` 是长期常态。** 全量 83.4 万首里只有 0.88% 有注疏。
   客户端必须隐藏空区块（不得渲染空标题），且**不得把「没有」表述成「加载失败」**——
   正确答案是引导用户去提问。
3. **`annotation_sources` / `annotation_citation` 必须展示成可点链接或文本。**
   它们是这个功能的可信度凭据：用户看到「引自《唐诗鉴赏辞典》」「古诗文网（CC0-1.0）」
   才能判断该不该信，也才有路径去读完整内容（`06 §7`）。

另外两条实测结论值得记在契约层面：

- **关掉模型思考链有 15 倍差距**（445 s → 28 s，`06 §6.2`）。这是走 Ollama
  原生 `/api/chat` 而非其 OpenAI 兼容层的唯一原因（兼容层不认 `think` 字段）。
- **已有注疏必须进问答的提示词且排在检索资料之前**（`06 §6.6`）。
  实测少了这一步，模型会给出自相矛盾的注音 —— 手里有权威内容却不给模型，
  等于让它凭印象猜。

### 6.4 版权开关

`01 §3.3` 决策为收录全量。合规风险由**服务端配置**承担，**不是客户端参数**：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `INCLUDE_COPYRIGHTED` | `true` | 置 `false` 后，`/poems`、`/search`、`/daily`、`/poems/random`、`/facets` 的计数**全部**排除 `is_public_domain=false` 的诗 |

客户端**不能**控制这个开关 —— 合规是运营决策，不该由客户端决定。`PoemDetail` 仍返回 `is_public_domain`，以便客户端在有需要时做展示区分。

> ⚠️ 已知不完美：离线包**不受此开关影响**（包已下发到用户设备，服务端无法收回）。真要合规下架 `d2-modern` 等包，需重新发布包并让客户端删除已装副本 —— 这是 `01 §3.3` 遗留问题的接口侧表现。

## 7. 版本化

- 路径前缀 `/api/v1`。**不做 `v2` 并行**，破坏性变更时直接升版本并强制客户端升级。
- 向后兼容的变更（**新增**可选字段、新增端点）不需要升版本。本文已按此原则预埋了 `annotation` 等字段，
  `06` 的落地正是按这条走的：**新增了 `annotation_background` / `annotation_citation` 与两个端点
  （`GET /poems/{id}/annotation`、`POST /poems/{id}/ask`），`/api/v1` 未变**。
  老客户端不认识新字段（`ignoreUnknownKeys`）也不会去调新端点，行为不受影响。
  期间移除的 `POST /poems/{id}/annotation` 是**尚未有客户端依赖**的端点（同一次迭代内新增又删除），
  不构成破坏性变更。
- `GET /packs` 的 `catalog_version` 与各包的 `version` 是**数据版本**，与 API 版本无关，二者独立演进。

## 8. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 浏览类接口的组织 | **收敛为 `/poems` 单端点 + 筛选参数** | 朝代/合集/词牌/作者本质是同一查询的不同 filter，多端点会重复分页/排序逻辑 |
| 列表返回内容 | **只返回 `excerpt`（首句）** | 列表 UI 只需首句判断是否点开；全文留给详情 |
| 搜索高亮 | **返回字符区间，不返回标记串** | 免去客户端解析 HTML，且消除注入面；区间按 **Unicode 码点**计，客户端须用 `codePointCount` 换算（`03 §4.5`） |
| 搜索排序 | **只承诺粗排序（标题>作者>正文，档内按 `weight`）**，不承诺档内精确顺序 | 服务端 FTS5+BM25，客户端 `LIKE` 匹配；强行对齐需客户端也引入 jieba 与倒排索引，代价远超收益（§5.1） |
| 搜索的数据源 | **有网走服务端，无网回退本地 `LIKE`** | 服务端全量 85.9 万首是本地已下载内容的超集；在线时用服务端结果**替换**而非合并（`04 §6.3`） |
| 客户端搜索实现（离线路径） | **`LIKE` 子串匹配，不建 FTS** | 离线时用户通常只装 1–2 个包（2 万首正文约 2 MB），LIKE 是毫秒级；建 FTS 要么塞 jieba（+2 MB APK），要么给包加分词字段（包体积 +60%，283→450 MB）。在线路径由服务端 FTS5 承担 |
| 注疏内容来源 | **从网络导入真人注疏**（方式二），不用 LLM 生成；冷门诗走**流式问答**（方式一） | 生成不可靠、无法流式、单首 30–60 s；而真人注疏零等待、可查证。见 `06 §1.1` |
| 注疏字段形态 | **保持字符串**（「词：义」一行一条） | 契约定的是字符串，改类型是破坏性变更；上游本身就是这个形态 |
| 问答是否落库 | **不落** | 一次问答针对某个具体问题，不是对整首诗的系统注疏 |
| 问答传输 | **SSE（POST）** | 单向推送；WebSocket 的双向与保活全用不上 |
| 收藏与历史 | **纯本地，预留 `user_id`/`synced_at`** | 省掉整个账号体系；预留字段使二期加同步无需改表 |
| 每日一诗的通知 | **服务端选诗 + 客户端 WorkManager 本地通知** | 无需 FCM 与厂商通道适配；离线仍可读缓存 |
| 每日一诗的主次 | **服务端选诗为主路径，本地选诗仅兜底，不做一致性要求** | 服务端要可操作性（人工干预/主题策划/调权），本地只要断网不开天窗；强行对齐会把两端池子与算法同时锁死 |
| 每日一诗候选池 | **即入库全量（859,591 首）**；`weight` 分 W1–W3 三层，只控制相对概率，不控制池子边界 | 池子大才能真正做节日/节气策划；离线可读由"缓存完整 `PoemDetail`"保证，不靠限制池子 |
| 客户端缓存每日一诗 | **预取 30 天，含正文** | 约 30 KB，可忽略；使离线可读性与"下载了哪些包"彻底解耦 |
| 列表默认排序 | **`weight` 而非 `id`** | 产品价值在精选发现，不在遍历 25 万首宋诗 |
| 离线包下载 | **静态 CDN，不经 API 服务** | 包是不可变大文件，API 服务不应承担其带宽 |
| 版权合规 | **服务端配置项，非客户端参数** | 合规是运营决策 |

## 9. 遗留问题

1. **`/facets` 的 `count` 是全表扫描** —— 85.9 万行做分组计数在 SQLite 上约数十毫秒，可接受；但若加上 `INCLUDE_COPYRIGHTED=false` 的过滤会稍慢。先上线实测，必要时改为定时预计算并缓存。
2. **搜索的"标题命中"如何定义** —— **已定**：标题档 = `title LIKE '%q%'`（客户端）/ FTS `title_tok` 匹配（服务端），二者均为**包含**语义而非完全相等。这样《静夜思》与《静夜思·其一》都算标题命中，符合用户预期（他记不清副标题）。因 §5.1 只承诺粗排序，两端对"包含"的实现差异不影响一致性。
3. **`sort=dynasty` 的语义** —— 是按 `dynasty_order` 升序（时间线）还是降序（从近到远）？产品默认取升序，但需确认。
4. **限流阈值未定** —— `RATE_LIMITED` 已定义错误码，但具体限流策略（按 IP？多少 QPS？）待部署阶段确定，个人项目可先不启用。
5. **`weight` 各层的具体数值需调参** —— §4.1 建议初值 `W3=100 / W2=30 / W1=1`，纯产品判断，无正确答案。
6. **W1 档内无排序能力**（§4.1）—— 85.7 万首权重相同，加权随机落到 W1 时实为均匀抽取。若需真实排序，**二期可选**引入外部清单：部编版语文教材必背篇目（小学 75 + 初中 61 篇）、王兆鹏《唐诗排行榜》前 100。二者均需人工核实录入，不属 ETL 管线预估范围。
7. **`W1` / `W2` 首数含未去重的原始条数** —— 与 `01 §2` 清单一致；去重后精确值待 `01 §10.2` 回填。
8. **⚠️ `weight` 分层在 ETL 里根本没有生效** —— 实测库内 `weight` **全部为 1**（832,852 首无一例外），
   `02 §4.1` 设计的 W3=100 / W2=30 / W1=1 三层只存在于文档里。后果有三：
   ①「每日一诗」的加权随机实际退化为全量均匀抽取（名篇不再有更高概率）；
   ② `/poems` 默认 `sort=weight` 退化为按 `poem_id` 排序，
   **`§3.3` 里「按 weight 排序使选本成员浮到前面」这个核心产品设计目前是失效的**；
   ③ `DAILY_POOL_MIN_WEIGHT` / `WEIGHT_W3` / `WEIGHT_W2` 三个配置项全部无效。
   注：注释功能（`06`）不受影响 —— 它的目标集按**合集白名单**选定，不依赖 `weight`。
   这是 `02` 契约之外的一个独立 ETL 缺陷，**需要单独修**（改 `etl/lib/pipeline.py` 的 weight 计算后重跑 load 阶段）。
