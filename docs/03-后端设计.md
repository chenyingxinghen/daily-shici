> 本文只设计**服务端**。客户端的 Room schema、包管理、UI 分层见 `04`。
> 上游数据形态与 ETL 管线见 `01`，接口契约见 `02`。

## 1. 选型与约束

### 1.1 为什么 SQLite 够用

| 质疑 | 数据 |
|---|---|
| 85.9 万行会不会太大 | SQLite 单表 85.9 万行属**小表**。行业经验值是千万行内无压力 |
| 库文件多大 | 正文约 283 MB 原始，去重后入库约 **320 MB**；加 FTS5 索引约 **450 MB** |
| 并发够吗 | 读多写极少。唯一写入是每日选诗的 1 行。**WAL 模式下读并发不受限** |
| 内存够吗 | 页缓存 `cache_size` 设 64 MB 即可，无需全量驻留 |

**结论：个人项目用 SQLite 是正解。** 换 PostgreSQL 的收益是并发写入与全文检索的中文分词，而本项目写入量接近零、分词用 jieba 外部处理即可。省下的是整个数据库运维。

### 1.2 关键约束

| 约束 | 值 | 影响 |
|---|---|---|
| 部署形态 | **单机单进程** | 不做多实例，故可用本地文件锁、内存缓存 |
| 写入频率 | 每日 1 行（`daily_pick`） | 全库只读，可放心加索引 |
| 大文件带宽 | 数据包 4–29 MB | **不经 API 服务**，走 nginx 静态（`02 §3.9`） |
| 无账号 | — | 无 session、无用户表、无鉴权中间件 |
| 中文检索 | jieba 分词 | SQLite 无内置中文分词器，见 §4 |

## 2. 数据库 Schema

### 2.1 表清单

### 2.2 核心表 DDL

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = NORMAL;

-- 朝代：双粒度（01 §5.2）。order 递增时 period 单调
CREATE TABLE dynasty (
  dynasty_id  INTEGER PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,        -- 唐
  period      TEXT NOT NULL,               -- 隋唐五代
  dynasty_order INTEGER NOT NULL,          -- 7
  is_public_domain INTEGER NOT NULL        -- 1
);

-- 作者：去重归一后（01 §4.2）
CREATE TABLE author (
  author_id   INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,               -- 曹操 / 作者待考
  dynasty_id  INTEGER NOT NULL REFERENCES dynasty(dynasty_id),
  poem_count  INTEGER NOT NULL DEFAULT 0   -- 冗余计数，见 §2.4
);
CREATE INDEX idx_author_name ON author(name);

-- 诗词主体
CREATE TABLE poem (
  poem_id     INTEGER PRIMARY KEY,         -- 稳定，01 §4.3
  source_id   TEXT NOT NULL UNIQUE,        -- 上游 id，溯源用
  title       TEXT NOT NULL,
  content     TEXT NOT NULL,               -- \n 分行
  author_id   INTEGER NOT NULL REFERENCES author(author_id),
  dynasty_id  INTEGER NOT NULL REFERENCES dynasty(dynasty_id),
  genre       TEXT NOT NULL,               -- shi / ci / ci_sao
  form        TEXT,                        -- 五言绝句 / 杂言（尽力而为）
  cipai       TEXT,                        -- 词牌，仅 genre=ci
  line_count  INTEGER NOT NULL,
  char_count  INTEGER NOT NULL,
  is_public_domain INTEGER NOT NULL,
  weight      INTEGER NOT NULL,            -- 1 / 30 / 100，01 §5.1 + 02 §4.1
  excerpt     TEXT NOT NULL                -- 正文首行，列表用（02 §2.1）
);

-- 列表默认排序是 weight DESC, poem_id ASC（02 §5.1 要求确定性次级排序）
CREATE INDEX idx_poem_weight   ON poem(weight DESC, poem_id ASC);
CREATE INDEX idx_poem_dynasty  ON poem(dynasty_id, weight DESC, poem_id ASC);
CREATE INDEX idx_poem_genre    ON poem(genre, weight DESC, poem_id ASC);
CREATE INDEX idx_poem_cipai    ON poem(cipai, weight DESC, poem_id ASC) WHERE cipai IS NOT NULL;
CREATE INDEX idx_poem_author   ON poem(author_id, weight DESC, poem_id ASC);
CREATE INDEX idx_poem_form     ON poem(form) WHERE form IS NOT NULL;

-- 合集
CREATE TABLE collection (
  collection_id INTEGER PRIMARY KEY,
  slug        TEXT NOT NULL UNIQUE,        -- tangshi-sanbai
  name        TEXT NOT NULL,               -- 唐诗三百首
  pack_id     TEXT REFERENCES pack(pack_id),
  builtin     INTEGER NOT NULL DEFAULT 0,  -- 是否在 seed 内置包
  sort_order  INTEGER NOT NULL
);

-- 合集归属：02 §2.2 的 collections 字段来源。故意不设唯一约束，
-- 因为同一首诗在同一合集中理论上只应出现一次，但上游存在重复条目，
-- 去重阶段已处理；此处保留普通索引即可
CREATE TABLE collection_member (
  collection_id INTEGER NOT NULL REFERENCES collection(collection_id),
  poem_id     INTEGER NOT NULL REFERENCES poem(poem_id),
  PRIMARY KEY (collection_id, poem_id)
);
CREATE INDEX idx_cm_poem ON collection_member(poem_id);   -- 详情页反查

-- 数据包（01 §6.3）
CREATE TABLE pack (
  pack_id     TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  tier        TEXT NOT NULL,               -- L0/L1/L2/L3
  version     INTEGER NOT NULL,
  poem_count  INTEGER NOT NULL,
  bytes_raw   INTEGER NOT NULL,
  bytes_gzip  INTEGER NOT NULL,
  sha256      TEXT NOT NULL,
  min_poem_id INTEGER NOT NULL,
  max_poem_id INTEGER NOT NULL,
  builtin     INTEGER NOT NULL DEFAULT 0
);

-- 每日一诗留档：滚动窗口 [今天-365, 今天+90]，02 §4.1
CREATE TABLE daily_pick (
  date        TEXT PRIMARY KEY,            -- YYYY-MM-DD
  poem_id     INTEGER NOT NULL REFERENCES poem(poem_id),
  pool_size   INTEGER NOT NULL,
  is_manual   INTEGER NOT NULL DEFAULT 0,  -- 人工干预标记
  created_at  TEXT NOT NULL
);

-- 筛选器计数缓存（02 §3.3 的性能兜底，见 §5.3）
CREATE TABLE facets_cache (
  id          INTEGER PRIMARY KEY CHECK (id = 1),
  payload     TEXT NOT NULL,               -- JSON
  generated_at TEXT NOT NULL
);
```

### 2.3 不建的表

| 不建 | 原因 |
|---|---|
| `user` / `session` / `token` | 无账号体系（`02 §6.1`） |
| `favorite` / `reading_history` | 纯客户端本地存储（`02 §6.2`） |

| `poem_tag` | 二期可选（`01 §5.5`） |

### 2.4 冗余字段的取舍

**`author.poem_count`** 冗余（可从 `poem` 聚合）。保留理由：作者页每次都要显示作品数，85 万行 `GROUP BY author_id` 每次约 50 ms，而作者页是高频入口。ETL 结束时一次性回填，运行期不变（全库只读）。

**`poem.excerpt`（正文首行）** 冗余。保留理由：SQLite 把大 TEXT 值存进 **overflow page**，一首 100 行的长诗其 `content` 会溢出到额外的页。列表查询若只取 `excerpt`，**这些溢出页完全不会被读取** —— 这是真实的 I/O 节省，尤其 `poet.song` 那批长诗。

> 注意：**这不是"覆盖索引"的收益。** 列表 SQL 还要取 `title` / `author_id` / `genre`，`idx_poem_weight` 无论如何都不可能覆盖查询，一定要回表。`excerpt` 省的是**溢出页 I/O**，不是回表。若要让列表走覆盖索引，得把 `title`/`genre` 等也塞进索引，代价是索引体积膨胀数倍 —— 不值得。

两个字段都是**以空间换 I/O**，量级在 MB 级（`excerpt` 约 20 MB），可接受。

## 3. 查询设计

### 3.1 列表查询（`02 §3.3`）

统一由 `/poems` 承接入参，动态拼接 WHERE。**筛选条件全部命中索引**：

```sql
SELECT poem_id, title, excerpt, author_id, dynasty_id, genre
FROM poem
WHERE (:dynasty_id IS NULL OR dynasty_id = :dynasty_id)
  AND (:genre IS NULL OR genre = :genre)
  AND (:cipai IS NULL OR cipai = :cipai)
  AND (:author_id IS NULL OR author_id = :author_id)
  AND (:form IS NULL OR form = :form)
  AND (is_public_domain = 1 OR :include_copyrighted)     -- 版权开关，见 §5.4
  -- keyset 分页：见下方说明，此处必须拆成两个条件，不能用行值比较
  AND (:cw IS NULL OR weight < :cw OR (weight = :cw AND poem_id > :cid))
ORDER BY weight DESC, poem_id ASC
LIMIT :limit;
```

要点：

- **keyset 分页而非 OFFSET。** 游标编码 `(weight, poem_id)` 二元组 —— 因为排序键是复合的，只带 `poem_id` 会导致跨 weight 档时翻页错乱。这是 `02 §1.3` 里"游标不透明"的具体实现。
- **⚠️ 排序键方向不一致，不能用行值比较。** `ORDER BY weight DESC, poem_id ASC` 是**混合方向**，而 SQL 的行值比较 `(weight, poem_id) < (:cw, :cid)` 隐含两列同向，会让 `poem_id` 那半翻错方向（重复或跳过整档）。必须显式拆成 `weight < :cw OR (weight = :cw AND poem_id > :cid)`。**这是本项目最容易写错的一处 SQL**，需单测覆盖跨 weight 档的翻页边界。
- **`ORDER BY` 必须与索引顺序逐字一致**（`weight DESC, poem_id ASC`），否则索引失效。`02 §5.1` 要求的"确定性次级排序"在此落地为 `poem_id ASC`。

**为什么次级排序选 `poem_id ASC` 而非 DESC**：`idx_poem_weight` 定义为 `(weight DESC, poem_id ASC)`。SQLite 可以反向扫描索引来满足 `poem_id DESC`，但那样 `weight` 也一并反向，与 `weight DESC` 冲突。**同向的定义让索引可被直接扫描**，这是索引能生效的前提。

**合集筛选走 `collection_member`**，单独一条 SQL：

```sql
SELECT p.poem_id, p.title, p.excerpt, p.author_id, p.dynasty_id, p.genre
FROM poem p
JOIN collection_member cm ON cm.poem_id = p.poem_id
WHERE cm.collection_id = :cid
  AND (:cw IS NULL OR p.weight < :cw OR (p.weight = :cw AND p.poem_id > :cid_cur))
ORDER BY p.weight DESC, p.poem_id ASC
LIMIT :limit;
```

（`collection_member` 的 `PK(collection_id, poem_id)` 使 `cm.collection_id = :cid` 高效；但排序仍要回到 `poem` 上做，故此处 JOIN 不可避免。合集最大 25 万首，实测需验证。）

### 3.2 游标编码

```python
# 游标 = base64(weight:poem_id)，对客户端不透明（02 §1.3）
def encode_cursor(weight: int, poem_id: int) -> str:
    return base64.urlsafe_b64encode(f"{weight}:{poem_id}".encode()).decode().rstrip("=")

def decode_cursor(s: str) -> tuple[int, int]:
    raw = base64.urlsafe_b64decode(s + "=" * (-len(s) % 4)).decode()
    w, p = raw.split(":")
    return int(w), int(p)
```

**不做签名。** 游标只影响分页位置，被篡改的后果是用户看到错误的一页，无安全影响。加签名徒增复杂度和密钥管理。

`sort` 变化时游标失效（`02 §1.3`）：`decode_cursor` 返回的 `weight` 若不在当前 `sort` 的排序键体系内，直接从头开始。

### 3.3 条件索引与查询计划

新增筛选维度时**必须同步加索引**，否则会退化为全表扫描。上线前用 `EXPLAIN QUERY PLAN` 逐个验证：

```sql
EXPLAIN QUERY PLAN
SELECT poem_id FROM poem WHERE dynasty_id=7 AND genre='shi'
ORDER BY weight DESC, poem_id ASC LIMIT 20;
-- 期望：SEARCH poem USING INDEX idx_poem_dynasty (dynasty_id=?)
-- 若出现 SCAN poem 则索引未命中，必须修
```

**这是本设计的性能红线**：85 万行全表扫描约 300 ms，用户可感知；走索引约 2 ms。

### 3.4 随机漫游（`02 §3.5`）

```sql
-- 不用 ORDER BY RANDOM()：85 万行全表排序，约 800 ms
SELECT * FROM poem
WHERE poem_id >= (SELECT ABS(RANDOM()) % (SELECT MAX(poem_id) FROM poem))
  AND (<其他筛选条件>)
ORDER BY poem_id LIMIT 1;
```

`poem_id` 连续无空洞（`01 §4.3` 顺序分配），故 `RANDOM() % MAX` 是均匀的。若带筛选条件导致命中率低，重试至多 5 次，仍不中则退化为一次 `COUNT` + `OFFSET`（仅此路径允许 OFFSET，因为只取一行）。

## 4. 全文检索

### 4.1 中文分词问题

**SQLite FTS5 内置的分词器均不支持中文**：`unicode61` 按空格与标点切分，中文会被整段当成一个 token；`trigram` 只支持子串匹配，无法做词级检索。

三条路线：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. jieba 预分词** ★选用 | ETL 时用 jieba 把 `title`/`content` 切成空格分隔的词，存入 FTS 表，查询串同样分词 | 检索质量最好；索引体积增约 60%；纯 Python，无编译依赖 |
| B. `simple` 分词器 | 自写 C 扩展或用现成轮子 | 检索质量依赖实现，且引入编译产物，与"无 Docker、纯 Python"的约束冲突 |
| C. `trigram` | 无需分词，直接子串匹配 | 中文短查询（2–3 字）会命中过多；且无法按词排序。**适合做兜底，不适合做主检索** |

**选 A，并用 C 做兜底**（见 §4.4）。

### 4.2 FTS 表结构

```sql
-- 外部内容表：正文不重复存储，省约 280 MB
CREATE VIRTUAL TABLE poem_fts USING fts5(
  title_tok,      -- jieba 分词后的标题
  author_tok,     -- 分词后的作者名
  content_tok,    -- jieba 分词后的正文
  content='',     -- 外部内容模式，数据由 ETL 直接插入
  tokenize='unicode61'
);
```

`content=''` 使 FTS 表**不自带正文副本**，只存倒排索引。这是体积上的关键决策 —— 否则库文件从 450 MB 涨到 730 MB。

代价：无法用 `snippet()` / `highlight()` 辅助函数（它们需要原文）。**这对我们无损** —— `02 §2.3` 要求返回的是**字符区间**而非标记串，本来就要自己算。

### 4.3 搜索实现

```python
def search(q: str, scope: str, limit: int, cursor):
    toks = " ".join(jieba.cut_for_search(q))
    # 标题权重高于作者高于正文（02 §3.6 排序要求）
    sql = """
      SELECT f.rowid AS poem_id,
             bm25(poem_fts, 10.0, 5.0, 1.0) AS rank,
             p.weight
      FROM poem_fts f JOIN poem p ON p.poem_id = f.rowid
      WHERE poem_fts MATCH :toks AND {COPYRIGHT_CLAUSE}   -- 见 §5.4，启动时注入常量
      ORDER BY rank ASC, p.weight DESC, p.poem_id ASC
      LIMIT :limit
    """
```

- `bm25(poem_fts, 10.0, 5.0, 1.0)` 的列权重实现"标题 > 作者 > 正文"（`02 §3.6`）。**权重值是调参项**，上线后按实际效果调。
- **`ORDER BY` 尾部必带 `p.poem_id ASC`** —— 与 `02 §5.1` 的"确定性次级排序"要求一致，否则同分结果顺序不稳定，客户端本地 FTS 与服务端会对不上。
- 前缀匹配：查询串末词加 `*`（`"落霞"*`），支持"边打边搜"。

**`COPYRIGHT_CLAUSE` 是唯一被字符串拼进 SQL 的片段**，取自启动时的配置常量（值域只有 `"1"` 与 `"p.is_public_domain = 1"` 两种），**绝不含用户输入**。其余所有值一律走参数化占位符。这是全项目唯一允许的 SQL 拼接点，须在 code review 中显著标注。

`scope` 参数（`02 §3.6`）实现为列限定：`title_tok:词` / `author_tok:词` / `content_tok:词`，追加在 `MATCH` 右值中（同样经 §4.4 的转义）。

### 4.4 兜底与边界

| 情况 | 处理 |
|---|---|
| jieba 切出的词全部 < 2 字 | 改用 `trigram` 子串匹配。古诗中"月""风"这类单字查询很常见，纯词级检索会漏 |
| 查询串含 FTS5 特殊字符（`"` `*` `(` `-` `:`） | **必须转义**，否则 `MATCH` 语法错误导致 500。用双引号包裹整个 token 并转义内部引号 |
| 查询结果为空且 `scope=all` | 回退到 `LIKE '%q%'` 扫描（限 `title` + 前 200 字）。慢但只在零结果时触发 |
| `q` 长度 > 64 | 返回 `INVALID_PARAM`（`02 §1.4`） |

**FTS5 注入防护**：`MATCH` 的右值不接受参数化占位符做语法解析，必须把用户输入**当数据而非语法**处理 —— 转义为短语查询（`"词1 词2"`）而非裸拼接。这是本项目唯一的注入面，须有单测覆盖。

### 4.5 高亮区间计算（`02 §2.3`）

因为 FTS 表不含原文，`snippet` 与 `highlights` 需在应用层算：

```
1. 从 poem.content 取命中句（按 \n 切分，逐句查是否含查询词）
2. snippet = 命中句（超 60 字则截断，保持标点完整）
3. highlights = [snippet.find(词) 的区间]，合并重叠区间
4. 返回字符区间，左闭右开（02 §2.3）
```

**注意**：中文的"字符"在 Python 里是 `str` 索引，在 Kotlin 里是 UTF-16 code unit —— **生僻字（`01 §3.4` 提到保留繁体的那批）会成为代理对，两端索引不一致**。契约规定索引按 **Unicode 码点**计，客户端需用 `codePointCount` 换算。这一条必须写进 `04` 并在两端各有单测。

## 5. 业务逻辑

### 5.1 每日选诗定时任务（`02 §4.1`）

```python
# 每日 00:05 触发（避开 00:00 的整点资源竞争）
def refill_daily_window():
    today = date.today()
    need = [today + timedelta(d) for d in range(0, 91)]        # 未来 90 天
    have = {row.date for row in db.query("SELECT date FROM daily_pick")}
    for d in need:
        if d.isoformat() not in have:
            pick_and_store(d)
    # 清理窗口外（> 365 天前）
    db.execute("DELETE FROM daily_pick WHERE date < ?",
               ((today - timedelta(days=365)).isoformat(),))
```

`pick_and_store(d)`：

```
1. 若该日期已有 is_manual=1 的记录 → 跳过（人工预置优先）
2. 取近 365 天已用过的 poem_id 集合（窗口外的不算，因其已被清理）
3. 候选 = SELECT poem_id, weight FROM poem WHERE poem_id NOT IN (已用)
4. 加权随机：按 weight 累加前缀和，随机取点
5. INSERT INTO daily_pick
```

**加权随机的实现要点**：不能 `ORDER BY RANDOM() * weight` —— 那是"随机排序后乘权重"，不是加权抽样。正确做法是前缀和 + 二分：

```python
total = sum(w for _, w in candidates)
r = random.randrange(total)
acc = 0
for pid, w in candidates:
    acc += w
    if r < acc:
        return pid
```

85.7 万候选每次重算前缀和约 100 ms，可接受。若嫌慢，可预计算累积权重表并缓存在内存（全库只读，缓存永不失效）。

**并发安全**：定时任务与 API 进程可能是同一进程的 APScheduler 任务，也可能是独立 cron。**用 `daily_pick.date` 主键冲突做幂等保护**，插入用 `INSERT OR IGNORE` —— 多实例重复触发不会写出两条。

### 5.2 筛选器计数（`02 §3.7`）

`/facets` 的计数是全表 `GROUP BY`，85.7 万行约 **200 ms**（`02 §9.1` 已标注为待观测项）。策略：

- 首次请求时计算，写入 `facets_cache`，`Cache-Control: max-age=86400`。
- 之后的请求直接读缓存。
- **ETL 结束或版权开关变更时主动失效**（删除该行），而非等 TTL 过期。
- 词牌约 1,000 条需要 `GROUP BY cipai`，是其中最慢的一段；单独缓存。

### 5.3 作者作品数与作者页

`author.poem_count` 由 ETL 回填（§2.4）。`/authors/{id}` 直接读，无聚合。
作品列表走 `/poems?author_id=`，命中 `idx_poem_author`。

### 5.4 版权开关（`02 §6.4`）

**配置项 `INCLUDE_COPYRIGHTED` 是全局的，不在每个请求里解析。**

实现：进程启动时读配置，写入一个 SQL 片段常量，注入所有查询：

```python
# ON  → 不过滤（默认）；OFF → 排除受版权保护者
COPYRIGHT_CLAUSE = "1" if cfg.INCLUDE_COPYRIGHTED else "is_public_domain = 1"
```

> ⚠️ **不能借 `weight` 实现这个开关。** 早期设计曾用 `weight >= :min` 代替，理由是 `weight` 在索引列内。但**该技巧在 `weight` 分层调整为 W1–W3 后已失效** —— `01 §5.2` 把 `data2/*` 全部并入 W1，受版权保护的诗与公有领域的 W1 诗权重**同为 1**，`weight >= 1` 过滤不掉任何东西。必须直接用 `is_public_domain`。
>
> 代价是它无法作为索引范围约束，只能做行过滤。但本查询本就需访问 `poem` 行（要取 `title`/`excerpt`），**行过滤的边际成本可忽略**。若实测 `/facets` 的计数受影响（`02 §9.1`），再考虑加 `CREATE INDEX idx_poem_pd ON poem(is_public_domain, weight DESC, poem_id ASC)` 局部索引。

> ⚠️ 已知不完美（`02 §6.4` 已标注）：**离线包不受此开关影响**。包一旦下发到设备，服务端无法收回。真要合规下架，须重发包 + 客户端删除已装副本。

### 5.5 随机漫游的离线等价性说明

`02 §5.1` 要求两端语义一致。**随机漫游是唯一明确豁免的端点** —— 随机的本质就是不确定，两端结果不同属预期。但**筛选条件必须一致**（`dynasty` / `genre` 等），否则会出现"在线随机唐诗、离线随机宋词"这种荒谬情况。

## 6. 应用结构

```
server/
  app/
    main.py                 # FastAPI 实例、中间件、异常处理
    config.py               # 环境变量（含 INCLUDE_COPYRIGHTED）
    db.py                   # SQLite 连接池、PRAGMA 设置
    routers/
      daily.py              # /daily, /daily/batch
      poems.py              # /poems, /poems/{id}, /poems/random
      search.py             # /search
      facets.py             # /facets
      authors.py            # /authors/{id}
      packs.py              # /packs
    schemas/                # Pydantic 响应模型（对应 02 §2）
    services/
      query.py              # 动态 WHERE 拼接、游标编解码
      fts.py                # jieba 分词、FTS5 查询、转义
      highlight.py          # 字符区间计算（§4.5）
      daily.py              # 选诗算法（§5.1）
      cache.py              # facets 缓存
    jobs/
      daily_pick.py         # APScheduler 任务
  data/
    poems.db                # ★ ETL 产物，不纳入版本控制
  packs/                    # ★ 数据包静态文件，nginx 直接服务
  tests/
```

**连接处理**：SQLite + FastAPI 的常见坑是每请求新建连接。做法：

- 用 `check_same_thread=False` 的单一写连接（只有定时任务用）。
- 读连接用 `threading.local()` 每线程一个，**FastAPI 的同步路由跑在线程池里**，故每线程复用即可。
- **不用 `aiosqlite`** —— 全网只读 + 页缓存命中，同步阻塞耗时在微秒级，引入 async 驱动只会增加复杂度。

**响应模型**：所有响应经 Pydantic 模型序列化（`schemas/`），确保 `02 §2` 的字段名与类型不被意外改动。`annotation` / `translation` / `appreciation` 三个预留字段在模型里默认 `None`。

## 7. 部署

### 7.1 拓扑

```
        ┌─────────────┐
用户 ───▶│   nginx     │
        └──┬───────┬──┘
           │       │
   /api/v1 │       │ /packs/*.jsonl.gz   ← 静态文件，4–29 MB
           ▼       ▼
     ┌──────────┐  ┌──────────┐
     │ uvicorn  │  │ 磁盘     │
     │ (API)    │  └──────────┘
     └────┬─────┘
          ▼
     poems.db (SQLite, WAL)
```

**数据包必须由 nginx 直接服务，不经 API 进程**（`02 §3.9`）。29 MB 的 `d2-ming` 包若走 uvicorn，会占满 worker 且拖垮同进程的 API 请求。

### 7.2 进程模型

- uvicorn **单 worker**。SQLite 写锁是全局的，多 worker 只会互相争锁；而本项目读多写近乎零，单 worker 足够。
- 定时任务用 APScheduler 跑在同一进程内（`BackgroundScheduler`），**不引 Celery** —— 一个每日任务不值得一套 broker。
- 若未来要扩到多实例，**先换 PostgreSQL**，不要试图让多个 uvicorn 共享 SQLite 文件（网络文件系统上的 SQLite 锁不可靠）。

### 7.3 运维要点

| 项 | 做法 |
|---|---|
| 备份 | 每日 `sqlite3 poems.db ".backup"` 到异地。库是只读的，备份可低频 |
| 数据更新 | ETL 产出新 `poems.db` → 校验 → **原子替换**（`mv` 同分区）+ 重启。不做在线迁移 |
| 日志 | 只记 ERROR 与慢查询（> 100 ms）。85 万行项目的 QPS 不值得全量访问日志 |
| 监控 | 一个 `/healthz` 返回库连接状态与 `daily_pick` 最新日期。**后者能发现定时任务静默失败** |
| 限流 | v1 不启用（`02 §9.4`）。nginx `limit_req` 即可，无需应用层 |

**`/healthz` 检查 `daily_pick` 最新日期**这一条值得强调：定时任务是本服务唯一的自动写入路径，它静默失败时 API 仍会正常返回（只是每日一诗不更新），**不主动检查就发现不了**。

## 8. 决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 数据库 | **SQLite（WAL）** | 85.9 万行是小表；写入近乎零；省下整个 DB 运维 |
| 驱动 | **同步 sqlite3，不用 aiosqlite** | 全网只读 + 页缓存命中，阻塞在微秒级；async 只增复杂度 |
| 分页 | **keyset，游标为 `(weight, poem_id)` 复合** | 排序键是复合的；单带 `poem_id` 跨 weight 档会错乱 |
| 游标签名 | **不签名** | 篡改只导致分页位置错误，无安全影响 |
| 中文检索 | **jieba 预分词入 FTS5 + trigram 兜底** | FTS5 内置分词器不支持中文；A 方案质量最好且无编译依赖 |
| FTS 存储 | **`content=''` 外部内容模式** | 省约 280 MB；代价是自算 snippet，而契约本就要字符区间，无损 |
| 搜索排序 | **bm25 列权重 10/5/1 + `poem_id` 兜底** | 实现"标题>作者>正文"（02 §3.6），且保证两端确定性 |
| 随机漫游 | **`RANDOM() % MAX(poem_id)`，不用 `ORDER BY RANDOM()`** | 后者 85 万行全表排序约 800 ms |
| `excerpt` / `poem_count` | **冗余存储** | `excerpt` 避开长诗 `content` 的 overflow page 读取；`poem_count` 避开每次作者页的 `GROUP BY`。是空间换 I/O，**不是覆盖索引**（§2.4） |
| 版权开关 | **进程启动时注入 `is_public_domain` 条件常量**；不可借 `weight` 实现 | `data2/*` 并入 W1 后，受版权保护的诗与公有领域诗权重相同，`weight` 无法区分（§5.4） |
| 定时任务 | **APScheduler 同进程，不引 Celery** | 每日一个任务不值一套 broker |
| 进程数 | **单 worker** | SQLite 写锁全局；扩展路径是先换 PG，不是多加 worker |
| 健康检查 | **必须检查 `daily_pick` 最新日期** | 定时任务静默失败时 API 仍正常，不主动查发现不了 |

## 9. 遗留问题

1. **`bm25` 列权重（10/5/1）与实际检索效果需调参** —— 上线后用真实查询验证"搜一句诗能找到全诗"的命中率。
2. **`/facets` 全表聚合约 200 ms**（§5.2）—— 已有 `facets_cache` 兜底，但首次请求仍慢。实测后可考虑 ETL 时预计算写死。
3. **`02 §9.2` 的"标题精确命中"定义未决** —— 影响 `bm25` 之外的排序加权。需与客户端约定同一规则。
4. **高亮区间的码点/UTF-16 换算**（§4.5）—— 契约规定按 Unicode 码点，客户端须用 `codePointCount`。**两端各需单测**，否则生僻字会错位。
5. **FTS5 `MATCH` 注入防护需单测覆盖**（§4.4）—— 本项目唯一注入面。
6. **`poems.db` 约 450 MB 的构建与替换耗时未实测** —— 若 ETL 重建超过可接受窗口，需改为增量更新而非全量替换。
